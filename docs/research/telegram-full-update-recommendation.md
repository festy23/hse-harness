# Обновление HSE HARNESS через Telegram без сложного CI/CD

Дата исследования: 18 октября 2026. База кода: `a60e37a`, выпуск 0.3.0.

Статус: результаты исследования и рекомендация для следующей спецификации.
Новый механизм здесь не реализован; npm, VPS и настройки бота не менялись.

## Решение для нашего проекта

Сохранить npm как канал доставки, long polling как транспорт Telegram,
существующий supervisor как управляющий процесс бота и systemd как менеджер
сервиса на VPS. Добавить небольшой стабильный запускатель, способный выбрать
проверенный engine, провести пробный запуск и восстановить предыдущую
совместимую пару engine + worker.

По умолчанию бот предлагает обновление владельцу в Telegram. Отдельная явно
включаемая настройка разрешает автоматическую установку совместимых выпусков.
Оба режима используют одну и ту же процедуру проверки, завершения текущих
операций, переключения и восстановления. Политика согласия не должна создавать
второй установщик.

Это проектная рекомендация по результатам трёх исследований, а не требование
Telegram или единственный принятый в отрасли способ развёртывания:

- [Telegram Bot API и интерфейс управления](telegram-bot-update-practices.md).
- [npm, systemd и варианты полного обновления VPS](vps-full-update-practices.md).
- [Аудит текущего механизма и перехода 0.2.3 → 0.3.0](current-update-gap-audit.md).

## Что подтвердилось по официальным источникам

1. Telegram поддерживает long polling и webhook как альтернативные способы
   получения updates. Для одной VPS webhook не требуется ради обновлений.
   Подтверждение `getUpdates` определяется offset; updates хранятся максимум
   24 часа. Короткий перезапуск можно пережить с долговечным offset, но это не
   гарантия восстановления после любого простоя.
   [Bot API](https://core.telegram.org/bots/api#getting-updates).
2. Inline-кнопка создаёт callback, который нужно быстро подтвердить через
   `answerCallbackQuery`; ждать завершения установки перед таким ACK нельзя.
   Сам ACK убирает ожидание в интерфейсе и не подтверждает успешное обновление.
   [CallbackQuery](https://core.telegram.org/bots/api#callbackquery).
3. `systemd` умеет перезапускать main process по политике завершения и применять
   ограничения стартов. `RestartForceExitStatus` позволяет отдельно обозначить
   ожидаемый выход ради обновления. Обычный `systemctl stop` не должен приводить
   к самовольному повторному запуску.
   [systemd.service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html).
4. `latest` — изменяемая метка. После согласия нужна конкретная версия и
   integrity, а не новая установка того, что случайно стало latest позже.
   [npm dist-tag](https://docs.npmjs.com/cli/v12/commands/npm-dist-tag/),
   [npm install](https://docs.npmjs.com/cli/v12/commands/npm-install/).
5. Успешный `npm publish` не означает немедленную доступность: npm выполняет
   проверку пакета перед установкой. Обычная задержка около пяти минут иногда
   увеличивается до 15 минут и дольше. Старый бот должен работать, пока новый
   архив ещё недоступен.
   [Объявление npm](https://github.blog/changelog/2026-07-28-npm-publish-time-malware-scanning-and-dual-use-metadata/).

## Что уже есть и чего не хватает

В 0.3.0 уже реализованы `/updates`, discovery раз в час, предложение не чаще
раза за 24 часа, owner-only кнопка, сохранённая заявка, проверка точной версии
и архива, неизменяемые каталоги выпусков, drain worker, probation, карантин,
возврат совместимого worker и уведомление о результате.
Настройка `updatesEnabled` сейчас разрешает переключать уже установленную
версию; она **не означает** автоматическое скачивание новых версий из npm.

Подробные ссылки на реализацию и тесты собраны в
[аудите](current-update-gap-audit.md).

Пробел — полный переход управляющего runtime:

- Launcher сейчас статически импортирует конкретный engine. Глобальный
  `npm install` не меняет этот import.
- Установщик runtime требует отсутствия живого бота. Его нельзя просто
  вызвать из callback внутри работающего процесса.
- Старый 0.2.3 отклоняет manifest 0.3.0, которому нужен supervisor 1.0.1.
  Это происходит до обновления глобального npm-пакета.
- Обычный restart через systemd не равен update drain и способен прервать
  принятые операции. Сначала нужен drain, затем перезапуск.

Удаление проверки `minSupervisorVersion` не решает эти проблемы.

Сопутствующие улучшения Telegram-интерфейса: подтверждение callback сейчас
ждёт последовательной очереди, а HTTP-ошибка не сохраняет структурированный
`retry_after`. Для будущего режима стоит вынести короткий UI ACK перед долгим
исполнением и учитывать серверную задержку при повторе уведомлений. Это не
повод менять Telegram-библиотеку или вводить новую инфраструктуру.

## Предлагаемый сценарий для владельца

Пример будущего интерфейса, а не перечень уже реализованных новых команд:

1. Бот сообщает: «Доступна версия 0.3.1. Обновление включает …».
   Кнопки: **Обновить**, **Напомнить завтра**, **Что изменилось**.
2. После нажатия быстро подтверждает кнопку и сохраняет запрос на конкретный
   выпуск. Повторное нажатие показывает состояние той же попытки.
3. Скачивает и проверяет выпуск, продолжая обычную работу.
4. При активной задаче пишет: «Обновление готово. Дождусь завершения текущей
   операции». Истечение ожидания откладывает обновление и возобновляет работу,
   не даёт разрешения убить модель или внешнюю запись.
5. Выполняет переключение с короткой паузой. Если достаточно сменить worker,
   использует нынешний путь; если нужен новый engine — путь через systemd.
6. После проверки запуска сообщает: «Обновлён до 0.3.1» либо «Новая версия
   не запустилась, восстановлена 0.3.0». Сетевой сбой задерживает доставку этого
   сообщения, но не теряет сохранённый итог.

`/updates` остаётся ручной проверкой. В следующей спецификации стоит определить
режимы `notify`, `auto` и отключение предложений, а также понятный статус
ожидания/подготовки/проверки/отката. Изменять режим обновлений вправе только
владелец в личном чате, независимо от LLM и состояния учебных источников.

| Политика | Поведение | Рекомендация |
| --- | --- | --- |
| Предлагать обновление | Проверять фоновой задачей, предлагать раз в сутки, устанавливать после кнопки | Режим по умолчанию |
| Обновлять автоматически | Та же проверенная процедура без отдельного клика, в разрешённое время и при безопасной точке | Только после явного включения владельцем |

Автообновление не должно определять безопасность только по слову patch или
minor: нужны совместимость runtime/данных и работоспособный путь восстановления.
После провала повтор той же версии прекращается до нового явного решения.
Для неизвестной совместимости и системных миграций автоматика не применяется.

## Минимальная техническая схема

Подготовка выпуска сохраняет нынешние ReleaseStore, ограничения установщика,
фиксацию version + integrity и изоляцию от пользовательских credentials.
Данные пользователя остаются вне каталога кода. Установка не заменяет файлы,
из которых ещё исполняется текущая версия.

Для смены engine нужен отдельный небольшой долговечный журнал загрузки:
подтверждённый engine, кандидат, предыдущая совместимая пара, фаза и идентичность
попытки. Схема журнала должна быть понятна стабильному запускателю и не подменять
учебное состояние или текущий журнал обновлений worker.

Порядок полного перехода:

1. Заранее подготовить и проверить весь выпуск; пробная проверка не запускает
   второй Telegram poller и не меняет живые учебные данные.
2. Текущий supervisor выполняет drain, flush, finish и подтверждает выход worker.
   При busy остаётся работать прежняя версия. Обычный stop budget systemd ещё
   не расходуется.
3. Долговечно зафиксировать handoff, завершить подготовительные процессы и
   освободить locks. Затем supervisor выходит с выделенным кодом.
4. systemd запускает тот же стабильный launcher. Его путь и unit не переписываются
   при каждом обновлении. Существующий `Restart=on-failure` перезапустит ненулевой
   код; если он объявлен штатным через `SuccessExitStatus`, требуется и
   `RestartForceExitStatus`. Код должен дойти до main PID сервиса.
5. Launcher запускает выбранный engine и ограничивает старт до активации worker.
   Для восстановления после зависшего старта недостаточно одного import:
   нужен независимый наблюдатель. Предпочтительный самодостаточный вариант —
   маленький bootstrap-процесс, который ждёт handshake/готовность дочернего
   engine, пересылает сигналы и использует boot journal для восстановления.
   Он не читает Telegram, не устанавливает npm и не управляет учебными задачами.
6. После проверки worker и окна стабильности зафиксировать успех. При отказе
   восстановить согласованную предыдущую пару engine + worker только после
   подтверждённого завершения кандидата. Если разрешение на активацию уже выдано,
   потеря ACK или heartbeat не даёт права убивать принятую работу ради отката:
   нужны проверка фактического владения и штатный drain. Ограничить попытки,
   сохранить причину и уведомление.

Альтернатива пункту 5 — импорт engine в main process с boot recovery и systemd
`Type=notify` + `TimeoutStartSec` до `READY=1`. Один `WatchdogSec` недостаточен:
он начинает контролировать процесс после завершения старта. Нужен явный
протокол готовности, а журнал сам по себе не обнаруживает зависание.
Выбор этих двух вариантов нужно зафиксировать при спецификации.
Постоянный отдельный updater daemon для обоих не требуется.

При нынешнем `KillMode=control-group` нельзя рассчитывать, что дочерний shell
переживёт остановку сервиса и закончит установку. Для обычного engine handoff
достаточно выхода main process: давать боту произвольный sudo не требуется.
[systemd.kill](https://www.freedesktop.org/software/systemd/man/latest/systemd.kill.html).

## Почему не предлагаем другую инфраструктуру сейчас

| Вариант | Оценка для существующего проекта |
| --- | --- |
| npm + имеющийся supervisor + systemd + небольшой launcher | Переиспользует нынешние проверки и состояние; рекомендуемый путь |
| Только systemd и versioned installs | Хорошая основа для нового маленького бота; у нас означает переписать уже работающие drain/rollback |
| Отдельный updater unit/helper | Полезен для изменений системных файлов; обычному user-owned engine не обязателен |
| Docker Compose | Допустимый deploy, но добавляет доставку образов, volumes и управление контейнером; сам не решает drain и откат данных |
| Webhook вместо polling | Не решает обновление локальных процессов; ради этой задачи не требуется |

Это оценка применимости, а не утверждение, что Docker или webhook плохи.
Сравнение и официальные источники:
[исследование VPS](vps-full-update-practices.md).

## Выпуск без нового CI/CD

Существующие проверки GitHub Actions можно сохранить. Разработчик по-прежнему
готовит версию и вручную публикует пакет в npm. После проверки доступности
точного архива бот обнаруживает его и предлагает установить.

Не нужны GitHub webhook на VPS, SSH secrets в Actions, собственный build server
или registry образов. Включать auto-apply на VPS и автоматизировать публикацию
в npm — разные решения; второе не является условием первого.

## Ограничения и ввод в эксплуатацию

- Первичная установка нового launcher потребует одного обслуживаемого перехода
  на VPS. Старая 0.2.3 не получает неизвестную ей команду задним числом.
- Короткая пауза допустима; нулевой downtime для одного экземпляра не заявляется.
  Drain может откладываться, пока выполняется принятый Pi-запрос.
- Откат кода использует актуальное состояние. Нельзя автоматически вернуть старую
  копию памяти и забыть уже отправленные сообщения или изменения календаря.
  Несовместимым миграциям нужен отдельный план.
- Полностью остановленный бот не примет Telegram-команду. Нужен системный
  менеджер и сохранённый ручной путь восстановления при отказе самого launcher,
  диска, Node или ОС. Их обновление не входит в обычный выпуск приложения.
- Exactly-once отправку через Bot API и неограниченное хранение updates обещать
  нельзя; сохранённые запросы и outbox уменьшают последствия повторов и сбоев.

## Проверки для будущей реализации

- Один poller/writer при обычном обновлении, повторной кнопке и reboot.
- Смена latest после нажатия не меняет одобренный target.
- Недоступный registry/ещё не опубликованный tarball не останавливает старую версию.
- Длинный Pi turn и внешняя запись удерживают drain; откладывание возвращает работу.
- Crash/reboot на каждой границе журнала, потерянный ACK и отсутствие свободного диска.
- Syntax error, ранний crash и зависший startup нового engine приводят к ограниченному
  восстановлению, а не вечному restart loop или двум активным процессам.
- Итог после успеха/отката сохраняется при недоступном Telegram.
- Сохраняются proxy drop-ins, учётные записи, календарь, очередь и история Pi.

Следующий результат реализации должен подтверждаться Linux/systemd E2E на
изолированной установке; один успешный `npm install` не доказывает полный handoff.
