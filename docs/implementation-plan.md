# План реализации Personal Study Assistant

Статус: план подтвержден пользователем 4 октября 2026 года. Основание — `docs/specification.md`. Код первой версии и локальные проверки подготовлены. Реальные аккаунты и VPS пока не подключаются: пользователь попросил сначала подготовить код.

## Архитектура первой версии

Один постоянно работающий TypeScript-сервис на VPS, использующий SDK обычного Pi coding agent. Он подключает источники, передает события агенту, выполняет разрешенные инструменты и отправляет уведомления. Pi остается agent runtime: сервис не реализует собственный цикл рассуждения или новую память.

| Часть | Обязанность |
| --- | --- |
| Telegram user API | Читать только выбранные чаты, получать историю/изменения, отправлять одобренные вопросы от аккаунта пользователя |
| Telegram Bot API | Личный диалог, сводки, напоминания, выбор статуса, подтверждение конкретной отправки |
| Яндекс IMAP | Читать текст учебных писем и историю с 1 сентября 2026; без анализа вложений |
| Календари (по умолчанию iCloud/CalDAV) | Читать расписание; поддерживать отдельный календарь событий и дедлайнов агента |
| Pi SDK | Одна продолжаемая учебная сессия с JSONL-историей и штатным compaction; анализ и вызовы инструментов |
| Планировщик | Сводки, напоминания и контроль отсутствия ответа; восстановление работы после перезапуска |

У одного пользователя одна основная сессия. Входящие сообщения, ответы пользователя и фоновые задания обрабатываются последовательно, чтобы два одновременных ответа не записали противоречащие изменения. Начальная обработка длинной истории идет порциями в той же сессии.

Проверенные зависимости: обычный Pi SDK 1.0.2, teleproto 1.229.1 для Telegram, ImapFlow 2.2.4 для IMAP; iCloud использует tsdav 2.4.0, iCalendar обрабатывается node-ical 0.27.3 и ical.js 2.2.1; Google Calendar использует REST API и выключен по умолчанию. Версии закреплены в package-lock.json. Новые agent/memory frameworks не добавляются. Интеграционные факты и первичные источники — в `docs/research/integration-facts.md` и `docs/research/library-apis.md`.

Изменение по запросу пользователя 6 октября 2026: iCloud включен, Google выключен через feature flag. Общий `CalendarCollection` скрывает протокол, `StudyCalendar` содержит учебные правила, фабрика лениво подключает выбранные провайдеры. Каждая роль имеет собственные provider/id; добавление адаптера не требует изменения планировщика или инструментов. Инструкция и границы CalDAV — в README.

## Что сохраняется и где

- История разговора, выводы агента, статусы и сведения о предметах — в штатной сессии Pi. Дополнительный семантический, векторный или графовый слой памяти не создается.
- События и дедлайны с описанием и ссылками — в отдельном календаре выбранного провайдера (с 6 октября 2026 — iCloud). Он используется и для восстановления расписанных уведомлений.
- Конфигурация подключений, курсоры чтения, идентификаторы доставленных напоминаний и ожидающие подтверждения отправки — небольшие служебные файлы сервиса. Это данные работы интеграций, а не вторая база учебных фактов. Чувствительные учетные данные хранятся отдельно от истории и логов.

Планировщику нужны устойчивые идентификаторы обязательства/события и уже выполненных уведомлений: иначе перезапуск будет создавать пропуски или повторные сообщения. Этот минимальный учет входит в интеграционную обвязку; отдельная SQLite-база не предлагается.

Сведения о дедлайне изменяются только вместе с обновлением связанного события/напоминаний и записью результата инструмента в Pi. Порядок операций и восстановление незавершенного изменения проверяются тестами. Календарь выбранного провайдера отражает учебные события; формулы оценивания не превращаются в искусственные события календаря.

## Инструменты агента и подтверждения

Доступ агента ограничен нужными инструментами: чтение выбранных источников/истории, календарь, поиск официальных страниц ВШЭ, подготовка уточнения, личное уведомление. Не предоставлять агенту универсальный shell или чтение секретов для обхода согласования. При инициализации SDK явно задать разрешенный набор tools и контролируемый resource loader, без автоматического подключения произвольных расширений.

Отправка в группу — отдельный путь исполнения:

1. Агент готовит точный текст, выбранный чат и основание вопроса.
2. Бот показывает пользователю черновик.
3. Сервис получает подтверждение от настроенного владельца бота в личном диалоге.
4. Сервис отправляет ровно согласованный текст в согласованный чат от пользовательского аккаунта. Подтверждение одноразовое; изменение текста/чата требует нового одобрения.
5. Через сутки без ответа сервис сообщает пользователю; повторно сам не отправляет.

Учебное сообщение, письмо или веб-страница не могут служить подтверждением отправки. Указания внутри источников рассматриваются как источник учебной информации, а не инструкции управлять инструментами.

Изменения исходного календаря расписания проходят аналогичную проверку одобрения конкретного изменения. Начальное чтение расписания требует только read access; для выполнения согласованной правки нужны права записи выбранного календарного провайдера. Право редактировать собственный календарь агента не означает право менять расписание.

## Правила календаря и уведомлений

Для обязательства сохраняется связь с источником и событием календаря агента. Повторное объявление обновляет существующее обязательство. При переносе пересчитываются события и еще не отправленные напоминания; при отмене они снимаются.

«Сделал» продолжает напоминания о сдаче, «сдал» прекращает их. Работа, срок которой прошел, остается непроверенной до сообщения пользователя; автоматическая отметка сдачи недопустима.

Время везде Europe/Moscow. Сводки — 10:00 и 20:00. Напоминания — за три дня, сутки и час. Для даты без времени граница — 00:00 указанной даты по личному правилу пользователя. Для спорных дат используется самая ранняя, с явной пометкой о конфликте. Срочные уведомления допустимы ночью.

Планировщик отправляет известные напоминания без нового LLM-запроса на каждую отправку. Анализ новых сообщений и текст сводок выполняются через Pi. Перенос должен отменять устаревшие уведомления, а повторная доставка одного входящего события — не создавать новый дедлайн.

После перезапуска сервис догоняет непрочитанные источники и восстанавливает таймеры. Уже прошедшие интервалы напоминаний не отправляются пачкой: сообщается текущая срочность, без создания впечатления, что уведомление было доставлено вовремя. Сбой Telegram/почты/календаря/модели явно отражается в состоянии работы и сообщается пользователю доступным каналом.

Точное предупреждение об остатке подписки зависит от проверенного источника данных провайдера. Статистика токенов Pi не используется как выдуманный счетчик Pro-квоты. Платного API-fallback нет.

## Порядок реализации

1. **Минимальный работающий путь:** сервис + Pi SDK + подписочный вход + личный Telegram-бот. Сообщение пользователя обрабатывается в сохраняемой сессии; после перезапуска разговор продолжается. Проверить каталог доступных моделей и возможность получения данных о лимитах.
2. **Источники:** подключить выбранные Telegram-чаты и учебный IMAP-ящик; обрабатывать только текст. Реализовать возобновление чтения и первоначальную историю с 1 сентября 2026. Новые данные во время начальной загрузки также не теряются. Telegram-история загружается назад до нужной даты; IMAP-курсор привязывается к папке и UIDVALIDITY.
3. **Обязательства и календарь:** связывать объявления, сроки, переносы, отмены и статусы; читать расписание и вести отдельный календарь. Начальную подборку показать пользователю для отметки уже сданного. CalDAV синхронизировать полными проверенными снимками с обнаружением удалений; использовать ETag при изменении и удалении. Google по умолчанию отключен feature flag. Для опционального Google Calendar отделить начальную загрузку от получения изменений по syncToken; при истечении токена выполнить полную пересинхронизацию.
4. **Уведомления:** внедрить устойчивое расписание напоминаний, сводки и срочные сообщения. Проверить задержки/повторы после перезапуска и временных сбоев.
5. **Уточнения и сведения о предметах:** добавить одобрение отправки и контроль ответа; дать агенту доступ к официальным источникам, перенести проверенные правила в его сессию с ссылками. Пробелы в формулах остаются явными.
6. **Размещение:** запуск и перезапуск на Linux VPS, проверка здоровья подключений, сохранности сессии и восстановления после сбоя. Конкретные ресурсы и поставщик выбираются по требованиям работающего сервиса в бюджете пользователя.

## Проверки приемки

Контрольный набор исходных сообщений с заранее известными обязательствами должен покрывать:

- повторное объявление одного задания;
- перенос, отмену и конфликт сроков;
- дату без времени и «к следующему семинару»;
- сделанную, но не сданную работу;
- остановку напоминаний после сдачи;
- добавление/обновление/отмену события агента без самовольного изменения расписания;
- одобренный и неодобренный вопрос, изменение текста после одобрения, повторное подтверждение и отсутствие ответа сутки;
- обработку письма/сообщения повторно и перезапуск между операциями;
- сохранность всех контрольных дедлайнов после штатного compaction и продолжения сессии.

Логика времени, подтверждений и повторной обработки проверяется детерминированно. Для понимания сообщений и compaction нужен отдельный прогон с реальной выбранной моделью: тесты на заглушках не подтверждают надежность памяти и извлечения.

Проверки должны подтвердить полный список заданий/источников и фактическую отправку нужных уведомлений, а не только корректный текст ответа модели. Успешный тестовый прогон не является обещанием нулевых ошибок на любых будущих сообщениях.

Если штатная память провалит реальные контрольные сценарии, зафиксировать конкретную ошибку и отдельно обсудить изменение памяти, как договорились. Не добавлять другой механизм заранее.

## Данные для настройки

Понадобятся выбранные чаты, адрес учебного ящика, доступ к календарю расписания и отдельному календарю агента, собственный бот, подписочный вход и VPS. Учебный годовой состав майнора и отсутствующие публичные правила можно уточнить по расписанию/текстовым источникам после подключения.

Авторизация внешних аккаунтов выполняется на этапе настройки. Пароли, коды входа и токены не публикуются в спецификации, Git или пользовательском диалоге.

Пользователь подтвердил спецификацию и план до начала реализации. Подготовлены сервис, инструменты, CLI настройки, контрольный прогон compaction и шаблон systemd. Локально проверяются сроки, очереди, восстановление, подтверждения и контракты интеграций; настоящий SDK Pi проверяется без модели на сохранение JSONL и разрешенные инструменты. Интеграционные проверки с живыми аккаунтами и моделью, полнота извлечения дедлайнов и работа на VPS остаются этапом приемки после подключения. Инструкция — `README.md`.
