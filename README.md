# HSE HARNESS

Персональный учебный секретарь для ВШЭ. Один TypeScript-сервис использует обычный Pi SDK, пользовательский Telegram, личного бота, Яндекс IMAP и Google / Яндекс / iCloud календари. Профиль и предметы задаются в CLI. Память — штатная JSONL-сессия Pi с compaction. Отдельного memory framework или SQLite нет.

Требования: [спецификация](docs/specification.md), устройство: [план](docs/implementation-plan.md). Для новой установки нужно подключить собственные аккаунты. Успех локальных тестов не подтверждает полноту извлечения дедлайнов выбранной моделью.

## Скачать и запустить

Node.js ≥22.19.0, npm. Проверено локально на Node 26.5.0. Версии зависимостей зафиксированы в package-lock.json; Pi 1.0.2.

```sh
git clone https://github.com/festy23/hse-harness.git
cd hse-harness
npm run harness
```

При первом запуске команда сама установит зависимости, включая Pi, и откроет меню настройки. На macOS/Linux можно пользоваться короткой командой `./hse`; на Windows — `npm run harness`. После `git pull` повторный запуск автоматически обновит зависимости, если изменился `package-lock.json`. Отдельные установка Pi, сборка и копирование `.env.example` для первого входа в меню не нужны.

Для работы каждый пользователь подключает свои Telegram-аккаунт и бота, подписку модели, почту и календари через мастер. Секреты и история владельца не скачиваются вместе с репозиторием. После настройки выбери «Запустить бота» или выполни `./hse start` / `npm run harness -- start`.

Репозиторий публичный: его можно клонировать без приглашения и GitHub-авторизации. Каждый пользователь настраивает свои аккаунты в CLI.

### Где Pi

Pi подключён как зависимость `@earendil-works/pi-coding-agent` версии `1.0.2` в `package.json`; исходники пакета устанавливаются в `node_modules/@earendil-works/pi-coding-agent/`. `package-lock.json` фиксирует версии зависимостей. Наш агент — это код в `src/`: правила и инструменты, Telegram, почта, календари и CLI вокруг Pi SDK. Поэтому отдельного клонирования исходного репозитория Pi не требуется.

Для разработки можно по-прежнему установить всё вручную через `npm ci`, затем выполнить `npm run check` и `npm run build`.

Меню **HSE HARNESS** позволяет настроить всё по шагам либо изменить отдельный раздел:

- Информация о тебе: имя, вуз, программа, группа, курс, учебный год, предметы, майнор/НИС.
- Telegram: скрытый ввод токена, вход в личный аккаунт, автоматический ownerId и поиск с отметкой чатов/каналов. История сообщений на этапе выбора не читается.
- Яндекс Почта: адрес, скрытый пароль приложения «Почта», проверка входа и выбор папок.
- LLM: подписочный вход OpenAI / ChatGPT через Pi и выбор модели из каталога подписанного аккаунта. Другие подписочные провайдеры пока не подключены.
- Календари: отдельно «откуда читать расписание» и «куда записывать дедлайны». Google, Яндекс и iCloud можно смешивать; календарь дедлайнов должен быть отдельным с правом записи.
- Запуск бота, просмотр сохранённых настроек, выход.

При входе меню показывает сине-белую заставку HSE HARNESS и терминальную стилизацию эмблемы ВШЭ. На широком окне используется крупная надпись, на узком — компактная; рисунок работает обычными символами, в том числе через SSH. `NO_COLOR=1 npm run harness` отключает цвета; при перенаправлении вывода и `TERM=dumb` рисунок не печатается.

Разделы отмечены значками: ✉️ почта, 📅 календари, 📡 каналы связи и ✈️ Telegram. Подписка OpenAI обозначается `>_ Codex`; общий набор обозначений также содержит ✳️ Claude, 🐋 DeepSeek и 🤖 AI для других провайдеров. Сейчас подписочный вход поддерживает только OpenAI, а канал связи — Telegram. 💬 Яндекс Мессенджер указан в разделе коннекторов как пока недоступный.

Стрелки и Enter выбирают пункт; в поиске чатов можно печатать название и отмечать результаты пробелом. Карточка показывает заполненные разделы и работающий процесс. В пошаговой настройке раздел можно пропустить или вернуться в меню. Ctrl+C внутри раздела или мастера `configure` отменяет текущий шаг и возвращает в меню; в главном меню завершает CLI. При прямом запуске отдельного раздела отмена завершает команду.

Статусы настроек обозначаются ✅ (сохранено) и ❌ (нужно настроить) в карточке и подсказках меню. После успешного сохранения раздела также появляется ✅.

Каждый завершённый раздел сохраняется целиком: новые значения `.env` записываются после успешной проверки и выбора источников. При ошибке или отмене восстанавливаются прежние настройки и заменённая авторизация Telegram/Google/Pi. Ранее завершённые разделы остаются сохранёнными. CLI не требует ручного редактирования файлов. Секреты вводятся скрыто и сохраняются с правами `0600`. Секреты, `data/`, `secrets/` и локальная конфигурация исключены из Git. Коды входа вводятся только в твоём терминале.

```sh
npm run harness -- configure  # все шаги
npm run harness -- start      # сборка и запуск одной командой
npm run harness -- status     # сохранённые настройки, без секретов
npm run harness -- telegram   # изменить только Telegram
npm run harness -- telegram-chats  # просмотр разрешённых чатов и правил доступа
npm run harness -- calendars  # изменить только календари
npm run harness -- help       # все команды
```

`npm run setup` без аргументов также открывает меню. `setup -- pi` открывает раздел модели, `setup -- google`, `icloud` и `yandex` — общий раздел календарей с выбором провайдеров; отдельная прежняя логика настройки не дублируется. CLI не запускает второй экземпляр при наличии работающего сервиса. Изменения профиля, источников и календарей применяются после перезапуска сервиса (Ctrl+C в терминале сервиса, затем `npm run harness -- start`). Для начала личного диалога открой своего бота и нажми Start. Проверить реальные соединения работающего бота можно командой `/status`.

Пункт **«📋 Разрешённые Telegram-чаты»** и команда `telegram-chats` показывают названия и ID выбранных источников, разрешение на чтение и отправку вопросов после подтверждения. Личный диалог с владельцем через бота показан отдельно. Просмотр не требует входа, не читает историю и не меняет настройки. Он отражает сохранённый список разрешений; право писать в группу/канал и текущая доступность Telegram этим просмотром не проверяются.

Для запуска личного бота нужны его токен и корректный ownerId. Остальные подключения могут завершаться после запуска: сбой календаря, отсутствие подписочного входа или модели отражаются в `/status` и не выключают личный диалог. Если профиль пока не заполнен, модель получает явное указание уточнять личные сведения; чужой профиль по умолчанию не подставляется.

## Подключения

1. **Pi / подписка.** `npm run harness -- model` предлагает сохранить текущий вход или войти заново через Sign in with ChatGPT провайдера `openai`, затем выбрать и сохранить модель. Постоянный UUID установки создается штатным SettingsManager Pi в `data/pi/settings.json` и передается OAuth через `getDeviceId`. Каталог берётся именно у подписанного аккаунта и фильтруется по поддержке Pi; встроенный список SDK не подтверждает доступность по подписке. `npm run setup -- models` остаётся командой просмотра каталога. [Контракт каталога OpenAI](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference). API-key fallback не используется. OAuth хранится в `secrets/pi-auth.json`; существующие credentials Codex не копируются.
2. **Telegram.** Создай своего бота через BotFather. Получи `api_id`/`api_hash` своего приложения на my.telegram.org. `npm run harness -- telegram` запросит эти данные и токен бота, авторизует личный аккаунт, автоматически определит ownerId и предложит выбрать учебные группы/каналы. Сохранённые, но сейчас недоступные чаты остаются в списке отмеченными: CLI не удаляет их молча. После настройки открой ссылку на бота и нажми Start. Даже если аккаунт видит остальные диалоги, сервис не передает их сообщения модели.
3. **Почта.** Включи IMAP для учебного Яндекс-ящика и создай пароль приложения «Почта». `npm run harness -- mail` запросит адрес и пароль, проверит вход и предложит папки. Пустой `folders` означает все доступные папки кроме Trash/Junk/Drafts; можно указать явный список. Читаются основной текст/HTML как текст и заголовки, вложения не скачиваются для анализа. Административные ограничения учебного ящика проверяются при подключении.
4. **iCloud Calendar.** Создай в iCloud два разных календаря: расписание и «Учебный ассистент». Запусти `npm run harness -- calendars`, выбери iCloud и введи адрес Apple Account и пароль приложения, а не основной пароль Apple. Создать пароль можно в [Apple Account → Sign-In and Security → App-Specific Passwords](https://account.apple.com/); требуется двухфакторная аутентификация, см. [инструкцию Apple](https://support.apple.com/en-us/102654). Команда найдет календари и сохранит выбор. Расписание должно быть именно календарем iCloud; локальный календарь «На моем Mac» серверу недоступен. Для правок расписания нужны права записи.

**Яндекс Календарь:** в меню выбери Яндекс для нужной роли. Создай два календаря на [calendar.yandex.ru](https://calendar.yandex.ru). На [странице паролей приложений](https://id.yandex.ru/security/app-passwords) выбери «Календарь»; почтовый пароль для CalDAV не подходит. CLI сохраняет `YANDEX_CALENDAR_USERNAME` и `YANDEX_CALENDAR_APP_PASSWORD`, находит календари и предлагает выбор без копирования URL. Сервер `https://caldav.yandex.ru` и тип пароля описаны в [официальной инструкции Яндекса](https://yandex.ru/support/yandex-360/customers/calendar/web/ru/data-exchange/synchronization/sync-desktop).

Google client id/secret нужны только при выборе Google. CLI включает feature flags только выбранных календарных провайдеров; при сохранённой конфигурации iCloud Google остаётся выключенным и его OAuth не запускается. Секреты можно ввести через CLI или вручную в локальный `.env`.

## Выбор и устройство календарей

В `config.local.json` независимо выбираются две роли: `timetable` (расписание, правки после одобрения) и `agent` (дедлайны, автоматическое поддержание). Они должны указывать на разные календари.

```json
{
  "features": {"googleCalendar": false, "icloudCalendar": true},
  "calendars": {
    "timetable": {"provider": "icloud", "id": "https://pXX-caldav.icloud.com/.../schedule/"},
    "agent": {"provider": "icloud", "id": "https://pXX-caldav.icloud.com/.../deadlines/"}
  }
}
```

URL в примере условные; настоящие получит CLI. Для включения Google выбери его у нужной роли в `npm run harness -- calendars`: CLI запросит OAuth client ID/secret, выполнит вход и сохранит выбранные календари и feature flags. Допустимы разные провайдеры у двух ролей. Старые поля `timetableId`/`agentCalendarId` заменены на `calendars`.

`src/calendar/collection.ts` задает общий интерфейс чтения, интервалов, изменений, записи, удаления и переноса одного занятия. `StudyCalendar` содержит общие правила работ, дедлайнов и синхронизации. Адаптеры iCloud и Яндекса используют общую реализацию CalDAV; Google использует свой API. Фабрика загружает только выбранные и включенные провайдеры. Новый провайдер реализует `CalendarCollection` и регистрируется в фабрике/конфигурации; планировщик и инструменты агента менять не требуется.

CalDAV читает полные снимки выбранных календарей; идентификаторы предыдущего снимка сохраняются как служебный курсор для обнаружения удалений после рестарта. Ошибка чтения не считается пустым календарем. Запись и удаление используют ETag, создание — `If-None-Match: *`; конфликт не затирает чужую правку. Повторяющиеся занятия раскрываются с исключениями и переносами; согласованный перенос касается конкретного экземпляра и сохраняет остальные поля события. Google использует `syncToken` с полной пересинхронизацией после его истечения.

Ссылки на официальные инструкции и проверенные APIs: [интеграции](docs/research/integration-facts.md), [библиотеки](docs/research/library-apis.md), [подписочный вход](docs/research/pi-codex-subscription.md).

## Устройство CLI

`src/cli.ts` и совместимый `src/setup.ts` вызывают одну реализацию. Раздел настройки переиспользуется из меню, пошагового мастера и прямой команды.

`scripts/harness.mjs` запускается обычным Node.js до установки библиотек, проверяет версию Node и готовность зависимостей, затем загружает TypeScript CLI. `hse` — короткий запуск для macOS/Linux. `scripts/process.mjs` переиспользуется установщиком и CLI для запуска дочерних процессов и корректной остановки.

| Модуль | Ответственность |
| --- | --- |
| `src/cli/application.ts` | Команды, меню, последовательность разделов |
| `src/cli/terminal.ts`, `brand.ts`, `progress.ts` | Отображение, адаптивная заставка, ввод, индикатор работы и отмена |
| `src/cli/icons.ts` | Общие значки разделов и обозначения провайдеров |
| `src/cli/onboarding.ts`, `steps/` | Правила и сценарии пяти разделов |
| `src/cli/state.ts` | Проверка конфигурации, сохранение раздела, откат настроек и авторизации |
| `src/cli/connections/` | Подключения к сервисам; SDK загружается только для выбранного подключения |
| `src/cli/status.ts`, `service.ts` | Сохранённые настройки, проверка PID, сборка и запуск процесса |
| `src/cli/telegram-access.ts` | Просмотр разрешённых чатов и правил чтения/отправки |
| `src/cli/ports.ts` | Интерфейсы ввода и подключений для переиспользования и тестов |

Новый раздел добавляется в реестр `sections` и таблицу шагов. Сценарии работают через `SetupUI` и `SetupConnections`, поэтому их можно запускать с другой оболочкой или тестовым транспортом. Сетевые SDK не управляют меню и сохранением разделов. `help` и `status` не выполняют сетевых запросов; `status` показывает сохранённые предпосылки, а не исправность реальных подключений.

## Запуск и диалог

Основной канал общения — личный чат пользователя с Telegram-ботом после `/start`. Команды и переданный текст принимаются только от настроенного `ownerId` в этом личном чате. Ответы и уведомления отправляются через Bot API от аккаунта бота. Авторизованный личный Telegram-аккаунт обеспечивает чтение выбранных учебных источников; сообщения из групп рассматриваются как данные, а не команды владельца.

Личные сообщения обрабатываются перед ожидающими порциями источников после завершения текущего модельного хода. Это сохраняет доступность диалога во время большого первоначального импорта. Агент получает признак неподтвержденной сверки и количество ожидающих порций, чтобы не считать неразобранную историю проверенной.

`/start` и `/status` работают во время настройки остальных подключений. Обычный текст сохраняется в устойчивую очередь; до готовности Pi бот подтверждает сохранение сообщения. Подключения повторяются через 30 секунд. При следующей попытке сервис перечитывает выбранную модель и подписочный вход, поэтому после завершения настройки не требуется перезапуск. Учебная история начинает обрабатываться после готовности интеграций и Pi.

```sh
npm run build
npm start
```

При первом запуске сервис разбирает текстовую историю выбранных чатов и почты с 1 сентября 2026, затем предлагает сверить найденные задания. Сообщи, что уже сдано. После сверки `/ready` включает напоминания. Этот шаг не является отдельным согласованием правил агента: он предотвращает напоминания об уже сданных исторических работах.

- `/tasks` — текущие работы с известным сроком в календаре.
- `/status` — подключения, размер очереди, состояние напоминаний.
- `/ready` — начать напоминания после первоначального разбора/сверки.
- Обычный текст — вопросы, «сделал …», «сдал …», сведения о заданиях без срока.
- Вопрос в группу/правка расписания — бот показывает конкретный черновик и кнопки подтверждения. Текст/чат после подтверждения не меняются. Отправитель группового вопроса — личный аккаунт.

Сводки: 10:00 и 20:00 Москвы. Напоминания: за три дня, сутки, час. Срочные изменения — в любое время. Дата без часа означает начало указанного дня; «9 октября» → до 00:00 9 октября. «Сделал» сохраняет напоминания о сдаче, «сдал» прекращает.

Первый этап не выполняет ДЗ и не обрабатывает SmartLMS, PDF/скриншоты/голосовые. Правила предметов агент получает из проверенной справки и текстовых официальных страниц hse.ru; непубличные формулы и неоднозначности остаются явно непроверенными.

## Состояние и восстановление

`data/sessions/` — оригинальная штатная история Pi. `data/operations.json` — очередь еще не обработанного текста, hashes для дедупликации, курсоры источников, одноразовые черновики, расписанные уведомления и отметки доставки. Очередь освобождается после успешной обработки; постоянная отдельная база учебных фактов не ведется. Выбранный календарь агента содержит события/описания работ и актуальные сроки.

Нужен только один процесс на каталог `data/`. После рестарта он продолжает Pi-сессию и источники. Для Telegram используются сохраненные common/channel counters и raw difference; auth session сама по себе их не сохраняет. Когда сервер уже не отдает полный difference, сервис предупреждает о неполном покрытии и перечитывает доступную историю. Удаленные/недоступные аккаунту сообщения восстановить нельзя.

Сбой модели оставляет входящие данные в очереди. Известные расписанные напоминания отправляются без нового LLM-запроса. Достоверный остаток Pro-подписки пока не установлен: сервис сообщает о недоступности, но не показывает выдуманный процент. При сбое доставки уведомление не отмечается успешным. Если Telegram принял сообщение непосредственно перед аварией процесса, повтор возможен: Bot API не предоставляет ключ идемпотентности. Для групповых вопросов сохраненный MTProto random_id обеспечивает повтор с тем же идентификатором.

Длинный текст разбивается на части без усечения. Для почты есть настраиваемый предел `STUDY_MAX_TEXT_BYTES` (по умолчанию 2 MB текста на письмо): при достижении предела чтение не отмечается завершенным, курсор не продвигается и состояние почты становится недоступным. Нужно увеличить предел/разобрать конкретное письмо; оставшийся текст не считается успешно прочитанным.

Сохраняй `data/` и `secrets/` при переносе/резервном копировании, ограничивая доступ к ним. Логи показывают состояния подключений, не тексты учебных чатов и секреты.

## Проверка с реальной моделью

Локальный стенд без аккаунтов:

```sh
npm run test:e2e
```

Команда собирает проект, поднимает HTTP-стенд на loopback и запускает настоящий `dist/main.js` отдельным процессом с настоящим Pi SDK. Внешние Telegram/IMAP/CalDAV/Google и ответы модели заменяются тестовыми транспортами; выход во внешнюю сеть через fetch блокируется. Подмены доступны только тестовому preload, основной сервис их не подключает. Время ускорено, чтобы проверить напоминания и ожидание ответа сутки. Прогоны идут отдельно для iCloud, Google и Яндекса. Данные стенда — `data/e2e/latest/icloud/`, `google/` и `yandex/`; при повторном прогоне соответствующий каталог очищается. После прогона тестовые процессы останавливаются. Дополнительный сценарий запуска сохраняет результат в `data/e2e/latest/icloud-startup/`.

Проверены 13 сценариев для каждого из трёх провайдеров и отдельный сценарий незавершенной настройки (40 проверок): история/дубликаты, сроки, статусы, одобрение, ожидание ответа, правка расписания, перезапуск, ошибки модели/доставки, аварийный останов и ответы личного бота до готовности Pi/календаря. Модульные, контрактные и терминальные проверки запускаются через `npm run check`; они проверяют CLI, сохранение настроек, профиль и защиту подключений. На macOS/Linux для тестов настоящего терминала и групп процессов нужен Python 3; запуск самого бота требует только Node.js. [Отчет и ограничения](docs/e2e-report.md). Стенд проверяет исполнение заранее заданных модельных решений, а не понимание свободного текста настоящей LLM, авторизацию или реальные ограничения API.

После подписочного входа:

```sh
STUDY_EVAL_MODEL=your-model-id npm run eval
```

Прогон использует подписку, отдельную временную Pi-сессию, compaction и последующее восстановление. Проверяет перенос, «сделал, не сдал», отмену и дату без времени. Внешних сообщений/событий не создает. Временная сессия удаляется после проверки. Это небольшой контрольный сценарий; затем нужны реальные проверки подключений и извлечения по согласованным источникам.

## VPS

Размести проект в `/opt/hse-study-assistant` под отдельным пользователем `study`, установи Node/npm, выполни подготовку и подключения под этим пользователем. Шаблон [systemd service](deploy/study-assistant.service) использует этот путь; при другом размещении исправь WorkingDirectory/User/Group.

```sh
sudo cp deploy/study-assistant.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now study-assistant
sudo systemctl status study-assistant
journalctl -u study-assistant -f
```

Не запускай одновременно ручной процесс и systemd. Стоимость/ресурсы конкретного VPS еще не выбирались и не проверялись; целевой бюджет — до 2000 ₽/месяц на сервер.
