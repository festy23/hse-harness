# Полное обновление HSE HARNESS на одном VPS без сложного CI/CD

Проверено 18 октября 2026. Исследование первичных документов systemd, npm, Node.js и Docker; ничего на VPS не устанавливалось. Ниже отдельно отмечены документированные свойства платформ и предлагаемая архитектура проекта. Это исследование, не выполненная реализация.

## Рекомендация

Сохранить существующие npm-выпуски, supervisor, журнал переключения и systemd. Добавить небольшой стабильный bootstrap, который выбирает версию supervisor из проверенных отдельных каталогов и умеет восстанавливать прежний engine после неудачного пробного запуска. Перезапуск всего процесса запрашивать специальным кодом завершения через уже работающий systemd, без `sudo` из бота и без отдельного updater daemon.

По умолчанию оставить **уведомление + подтверждение владельцем в Telegram**. Полностью автоматический режим может использовать тот же механизм, но включается явно и только для совместимых выпусков. Публиковать npm можно вручную после существующих тестов: новая инфраструктура CI/CD для этого не требуется.

Это наш инженерный вывод для текущего продукта, а не предписанный Telegram или systemd единственный способ обновлять ботов.

## Что уже есть в проекте

Проверены `src/cli/system-service.ts`, `runtime/installation.mjs` и `runtime/releases.mjs` в текущем worktree:

- Системный unit запускает абсолютный Node и `runtime/launcher.mjs` от непривилегированного UID. Есть `Restart=on-failure`, `RestartSec=10`, `KillMode=control-group`, `TimeoutStopSec=90`, `NoNewPrivileges=true`.
- Установка копирует engine в отдельный каталог, проверяет неизменность существующего дерева, fsync-ит его; launcher пока содержит статический import конкретного engine. Это и есть шов, мешающий обычному обновлению worker заменить supervisor.
- Уже есть проверяемые npm-архивы, staging, runtime journal, active/previous, карантин и блокировки. Не нужно заново строить механизм доставки пакета.
- Текущий установщик сознательно не устанавливает engine поверх работающего процесса. Наличие новой npm-версии само по себе не переключает launcher.

Эти пункты — наблюдения локального кода, не утверждение о фактическом состоянии VPS.

## Документированные свойства, на которых можно строить решение

### systemd и Node.js

`systemctl restart` останавливает и запускает unit; `daemon-reload` перечитывает unit-файлы, а не обновляет код приложения. Возврат команды и состояние `active` не доказывают успешный прикладной диалог. [systemctl](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html)

`Restart=on-failure` перезапускает процесс с ненулевым exit status; `RestartForceExitStatus` позволяет явно выделить restart status. `TimeoutStopSec` ограничивает остановку; `Type=exec` обнаруживает ошибки запуска исполняемого файла, но не заменяет прикладную проверку здоровья. Эти опции давно существуют; ориентироваться надо на установленную версию systemd VPS, а не требовать новые возможности systemd 262. [systemd.service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html)

`KillMode=control-group` распространяет остановку на процессы unit; по истечении stop timeout оставшиеся процессы могут получить SIGKILL. Поэтому detached-дочерний «обновлятор», запущенный ботом в том же cgroup, не является независимым переживающим остановку помощником. Не следует менять KillMode на `process` или `none` ради такого обхода. [systemd.kill](https://www.freedesktop.org/software/systemd/man/latest/systemd.kill.html)

Обработчик SIGTERM в Node отменяет штатное поведение выхода: программа сама должна завершить очистку и закончить работу. SIGKILL обработать нельзя. Значит, сохранение состояния нельзя откладывать на необработанный `exit` или рассчитывать выполнить после принудительного убийства. [Node.js process](https://nodejs.org/api/process.html#signal-events)

Частые рестарты ограничиваются `StartLimitIntervalSec`/`StartLimitBurst`; при исчерпании лимита systemd перестаёт пробовать запускать unit. Следовательно, rollback надо осуществить до циклического исчерпания попыток, а не ждать бесконечных перезапусков. [systemd.unit](https://www.freedesktop.org/software/systemd/man/latest/systemd.unit.html#StartLimitIntervalSec=)

### npm

Одинаковые package name + version повторно опубликовать нельзя; npm публикует tarball integrity, а установка проверяет загруженные байты. Это позволяет фиксировать точную версию и checksum проверенного архива, но само по себе не удостоверяет отсутствие вредоносного кода у издателя. [npm publish](https://docs.npmjs.com/cli/v11/commands/npm-publish/)

`latest` — изменяемая метка версии, а не постоянная идентичность релиза. Для discovery подходит `latest`; после одобрения нужно устанавливать сохранённую точную версию, а не повторно разрешать `latest`. Иначе между нажатием кнопки и установкой может смениться целевой выпуск. [npm dist-tags](https://docs.npmjs.com/adding-dist-tags-to-packages/)

`--ignore-scripts` запрещает package lifecycle scripts при установке. Это уместно для текущего подготовленного/bundled пакета, если тест установки точного архива подтверждает работоспособность без них; автоматически включать произвольные install scripts от имени root нельзя. [npm install](https://docs.npmjs.com/cli/v11/commands/npm-install/)

npm имеет ограниченные retries для idempotent чтений при сетевых сбоях и HTTP 5xx; HTTP timeout по умолчанию может быть длинным. Нельзя считать это готовым повтором для любых 404 и завершённым общим бюджетом установки. В просмотренной официальной документации не найдено SLA «tarball гарантированно доступен через N секунд после публикации». [npm config](https://docs.npmjs.com/cli/v11/using-npm/config/#fetch-retries)

**Наше следствие:** metadata, точный tarball и manifest должны быть проверены до drain. При кратковременной недоступности свежего выпуска оставить старый процесс работать, повторить подготовку с backoff и ограниченным бюджетом; не объявлять новый релиз установленным и не откатывать исправный старый из-за ошибки скачивания.

## Минимальный handoff без нового updater daemon

Ниже — предложение для реализации, а не существующая функция.

### Подготовка, пока старый бот работает

1. Discovery получает стабильную версию из `latest`. Сохраняются точная версия, integrity, manifest, требуемые версии Node/bootstrap/supervisor, совместимость состояния.
2. Подготовка устанавливает/распаковывает выпуск в новый staging-каталог. Используются фиксированные package name и registry, лимиты времени/размера/диска и уже существующая проверка inventory. Готовое дерево не модифицируется при последующих запусках.
3. Чистый preflight проверяет возможность запуска entrypoint, целостность и совместимость. Preflight не включает polling Telegram, записи состояния пользователя или внешние действия.
4. После успешной подготовки создаётся предложение обновить конкретный проверенный выпуск. Авторизация привязана к владельцу, точному target и идентификатору попытки. Повторная кнопка возвращает существующий статус, не создаёт конкурентную установку.

### Переключение полного engine

5. После принятия команды supervisor прекращает приём новых операций, оставляет их в долговечной очереди/неподтверждённых updates и дожидается принятых действий и их записей. Подготовка не должна уже расходовать stop budget: плановый drain проходит **до** выхода и до SIGTERM systemd.
6. Если принятый Pi-запрос не завершился, обновление откладывается. Не нужно обещать «обновится за 90 секунд»: текущий контракт запрещает убивать принятый запрос ради обновления. Настройки и уведомления должны показывать это ожидание.
7. После quiescent и flush сохраняется отдельный boot journal: request ID, старый/новый engine и worker, integrity, фаза, счётчик trial и результат. Атомарный указатель/JSON фиксируется через существующий долговечный file fsync → rename → directory fsync. Одна только смена symlink не заменяет журнал и fsync.
8. Supervisor завершает worker, подтверждает отсутствие второго writer/poller, освобождает locks и заканчивает процесс специальным exit code, например 75. Если bootstrap — основной PID и spawn-ит engine, он обязан передать этот код наверх.
9. `Restart=on-failure` уже достаточно для ненулевого кода 75. Опционально при первоначальной настройке unit можно добавить `SuccessExitStatus=75` вместе с `RestartForceExitStatus=75`, чтобы осознанный handoff считался штатным и всё же перезапускался. Не добавлять только SuccessExitStatus: это выключит ожидаемый on-failure restart.
10. systemd запускает тот же стабильный bootstrap. Bootstrap читает journal, выбирает подготовленный engine и проводит trial. `ExecStart` и unit-file при обычной смене engine не переписываются, `daemon-reload` не нужен.

### Что именно должен делать bootstrap

Простой launcher с `import './new-engine.mjs'` или `exec new-engine` недостаточен: при parse error или зависшем старте новый engine не сможет сам выполнить rollback.

Минимальный надёжный вариант — небольшой bootstrap-процесс, остающийся родителем engine во время trial и обычной работы. Он читает ограниченный стабильный boot journal, spawn-ит выбранный engine, принимает минимальный versioned handshake/health, следит за стартовым deadline и пересылает сигналы. Он не читает учебные источники, не принимает Telegram updates, не скачивает npm и не обладает root. Это один launcher внутри того же unit, а не отдельный сервис обновлений.

Если candidate падает до committed health, bootstrap фиксирует отказ, запрещает повтор той же попытки и запускает подтверждённый engine после полной остановки candidate. При падении самого bootstrap systemd перезапускает его; непогашенный trial journal на следующем boot ведёт к старой подтверждённой версии. Нельзя повторять один и тот же candidate бесконечно.

Управление worker active/previous остаётся у существующего supervisor; boot journal отвечает только за выбор engine и согласованную с ним версию worker. Нужен явный контракт владения, чтобы две state machines не выбрали разные пары после падения. Пара engine + worker должна быть совместима и проверена до переключения.

**Helper/oneshot действительно понадобится**, если обновление требует менять root-owned unit, Node/ОС, bootstrap contract либо системную конфигурацию. Для обычного supervisor+worker выпуска это лишний компонент. Первоначальная установка bootstrap и, при необходимости, однократная правка unit всё равно выполняются обслуживаемо. В 0.2.3 не появится новая команда задним числом: первоначальный переход нельзя обещать провести кнопкой, которой установленная версия не знает.

## Здоровье, откат и сохранение состояния

Это наши критерии проверки для будущей реализации:

- Bootstrap видит ожидаемые engine/version/attempt ID, живой supervisor, единственный worker с writer lock и прогресс event loop/IPC. Проверяется возможность обслужить быстрые команды; полная синхронизация истории не является условием старта.
- Общее `active (running)` и один heartbeat недостаточны. Но временная внешняя недоступность Telegram/LLM/календаря тоже не должна автоматически объявлять новый код неисправным: локальную готовность и состояние источников показывать отдельно.
- Commit успешного trial выполняется после оговорённого окна стабильности; окончательное Telegram-уведомление сохраняется долговечно и доставляется после восстановления сети. Если Telegram недоступен, нельзя гарантировать немедленное уведомление.
- Откат кода не отменяет уже отправленные вопросы, календарные PUT или миграции данных. Для автоматики разрешены только обратно совместимые state/operations/protocol. Несовместимая миграция требует отдельного плана, backup и разрешения; старый процесс нельзя запускать вслепую поверх новой схемы.
- После перезагрузки VPS на любой фазе boot journal должен давать однозначное восстановление. Одновременно не запускаются два Telegram poller или два писателя пользовательского состояния.
- Возврат предыдущего кода не гарантируется при сломанном диске, ОС, Node, root filesystem или самом bootstrap. Сохраняются журнал и ручная команда восстановления через SSH.

## Сравнение простых вариантов

| Вариант | Что даёт | Цена/ограничение для HSE HARNESS | Решение |
|---|---|---|---|
| Существующий supervisor + стабильный bootstrap + systemd exit handoff | Сохраняет текущий worker drain, health, rollback; позволяет обновлять engine без sudo | Небольшой boot journal/handshake и одноразовая установка bootstrap | Рекомендуется |
| Только systemd + versioned npm installs | Простая схема для нового маленького бота, перезапуск всего выпуска | Удаление уже готового supervisor; drain, preflight, compatibility, trial/rollback всё равно нужны в launcher | Хорошая альтернатива с нуля, слабая причина переписывать существующее |
| Отдельный systemd oneshot updater/helper | Переживает остановку основного unit, может менять системные файлы | Дополнительный unit и privilege boundary; для user-owned engine не требуется | Оставить для системных обновлений, не вводить сейчас |
| Docker Compose | Упаковывает Node и зависимости; воспроизводимый deploy образа | Нужны image build/distribution, volumes, сеть/прокси и updater с контролем Docker; не устраняет state/rollback/drain | Не внедрять только ради кнопки обновления |

Docker официально описывает повторное создание контейнера приложения при обновлении, а `compose up --wait` ждёт running/healthy. Это пригодно для одного VPS, но не обещает бесшовное продолжение работы бота или автоматический откат состояния. [Compose production](https://docs.docker.com/compose/how-tos/production/), [compose up](https://docs.docker.com/reference/cli/docker/compose/up/)

Compose по умолчанию даёт остановке контейнера 10 секунд; `stop_grace_period` настраивается отдельно. Значит, контейнеризация сама не сохраняет принятый долгий Pi-запрос. [Compose service stop](https://docs.docker.com/reference/compose-file/services/#stop_grace_period)

Управление Docker daemon даёт широкие возможности на host; передавать `/var/run/docker.sock` боту ради обновления — нежелательное расширение полномочий. [Docker security](https://docs.docker.com/engine/security/)

## Полномочия и политика обновлений

systemd позволяет запускать системный service через `User`/`Group`; `NoNewPrivileges` ограничивает приобретение привилегий потомками, но не является запретом любых IPC-запросов к другим сервисам. Поэтому не надо дополнять бот произвольным `sudo systemctl`, root shell или общим npm exec. [systemd.exec](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html)

Предлагаемые правила продукта:

- Только фиксированный пакет `@ivan-boss/hse-harness` из настроенного доверенного registry, точная проверенная версия. Пользователь/LLM не передаёт shell-команду, произвольный URL пакета или имя unit.
- Root нужен первоначальному установщику unit/bootstrap. Рабочий update handler и staging выполняются владельцем установки без привилегий. User-owned код не даёт строгой защиты от компрометации того же UID, но не должен давать root-доступ ко всей VPS.
- Режим `notify` по умолчанию: проверка версии, одно предложение в сутки до решения, кнопки обновить/позже, статус и release notes. Режим `auto` отдельно включается владельцем, использует те же проверки и ждёт безопасного drain; минимум неизвестной совместимости означает запрос подтверждения.
- Разрешение относится к конкретному выпуску. Новая версия после одобрения старой не подменяет target. Рекомендуется максимум одна попытка автоматического trial; после rollback карантин, ясная причина и новое явное решение.
- Отключение обновлений отменяет подготовку, но не обрывает уже начатый безопасный handoff посередине. Поведение фиксируется в спецификации.

## Что обещать пользователю

Реалистично: подготовка на фоне, обновление одной кнопкой из Telegram, сохранение памяти/очереди, небольшая пауза при переключении, проверка запуска и возврат подтверждённой совместимой версии при выявленном сбое.

Не обещать: нулевой downtime на одном экземпляре; неизменную длительность долгого drain; exactly-once для всех внешних API; откат несовместимых данных без отдельной миграции; обновление самой ОС/Node/root-owned unit той же кнопкой; мгновенную доступность npm и Telegram.

## Минимальные проверки до реализации на VPS

1. Падение/kill/reboot в каждой фазе подготовки и trial, включая после переключения указателя до начала candidate.
2. Parse error, зависший старт, потеря health acknowledgement нового engine; старый engine запускается единожды с согласованным worker.
3. Одобрен target A, а latest стал B: устанавливается A с прежним integrity.
4. Скачивание/404/5xx/таймаут: старый бот продолжает отвечать, drain не начинался.
5. Долгий Pi turn и принятая внешняя запись: handoff ждёт; обычный stop/SIGTERM проверяется отдельно с реальным systemd cgroup.
6. Duplicate callback, повтор после перезапуска и исчерпание trial: нет параллельных npm/writer/poller.
7. Telegram недоступен после успеха/rollback: окончательное уведомление не теряется и уходит позднее.
8. Изменение supervisor/unit не уничтожает proxy drop-ins, credentials и пользовательские пути.
