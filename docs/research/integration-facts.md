# Проверка интеграций для Personal Study Assistant

Проверено 4 октября 2026 года. Объем: техническая реализуемость интеграций TypeScript-сервиса с обычным Pi SDK. Код, подключение аккаунтов и запросы с пользовательскими доступами не выполнялись. Выбор клиентских библиотек оставлен реализации; память повторно не исследуется.

## Вывод

Предложенная схема поддерживается API: Telegram пользовательского аккаунта для учебных групп, Bot API для личного интерфейса, IMAP для Яндекс Почты, Google Calendar API для расписания и отдельного календаря агента, Pi SDK для постоянной сессии и собственных инструментов. Это подтверждение интерфейсов, а не работающий интеграционный тест конкретных аккаунтов.

## Telegram

- История доступной группы получается через `messages.getHistory(peer, offset_id, offset_date, add_offset, limit, max_id, min_id, hash)`. Метод разрешен пользовательским аккаунтам. `offset_date` означает сообщения **до** даты, а не «после». Для разбора с 1 сентября 2026 года реализация должна постранично идти назад от текущей истории до границы `2026-09-01T00:00:00+03:00`, фильтруя по дате сообщения. Пагинация не гарантирует доступ к уже удаленным или скрытым аккаунту сообщениям. [getHistory](https://core.telegram.org/method/messages.getHistory), [пагинация](https://core.telegram.org/api/offsets).
- Новые сообщения, редактирования и удаления доступны в потоке Telegram API: `updateNewMessage`, `updateEditMessage`, `updateDeleteMessages`, отдельно для супергрупп/каналов — `updateNewChannelMessage`, `updateEditChannelMessage`, `updateDeleteChannelMessages`. После разрыва соединения используется сохраненное состояние `pts`/`seq` и механизмы `updates.getDifference`/`updates.getChannelDifference`; одного идентификатора последнего нового сообщения недостаточно для редактирований. Очень старые сообщения могут быть недоступны при восстановлении. [Работа с обновлениями](https://core.telegram.org/api/updates).
- Пользовательский API требует `api_id`/`api_hash` приложения и личного прохождения авторизации аккаунта; при включенной 2FA нужен соответствующий этап. Конкретный список доступных групп и доступность истории проверяются при подключении. [Регистрация приложения](https://core.telegram.org/api/obtaining_api_id), [авторизация](https://core.telegram.org/api/auth).
- Личный интерфейс можно реализовать обычным Bot API: `getUpdates` либо webhook, `sendMessage`, inline-кнопки и `callback_query` для подтверждения черновика. Неполученные обновления бота хранятся максимум 24 часа. Нельзя использовать эту очередь как долговременное хранилище подтверждений. [Bot API](https://core.telegram.org/bots/api#getting-updates).
- После подтверждения конкретного черновика пользовательский клиент вызывает `messages.sendMessage(peer, message, random_id, reply_to?)`. Метод поддерживает ответы; `random_id` предназначен для предотвращения повторной отправки. Доступ и право писать в конкретной группе обязательны. Ответы связываются с вопросом по идентификатору сообщения и `reply_to`. [Отправка](https://core.telegram.org/method/messages.sendMessage), [MessageReplyHeader](https://core.telegram.org/constructor/messageReplyHeader).

Инженерное следствие: проверка подтверждения должна происходить в коде сервиса непосредственно перед отправкой — пользователь, группа, точный текст, одноразовый статус черновика. Telegram API не предоставляет продуктового механизма «одобрить сообщение ассистента». При неизвестном результате сетевой отправки повтор используют с тем же `random_id`, а не как новое сообщение. Это вывод из поведения метода, не готовая функция Pi.

## Учебная Яндекс Почта

- Яндекс документирует IMAP `imap.yandex.ru:993` с SSL/TLS, включение доступа через почтовые клиенты и способа «Пароли приложений и OAuth-токены», создание пароля приложения для Почты. Для Яндекс 360 для бизнеса логин — полный адрес ящика. [Настройка других программ](https://yandex.ru/support/yandex-360/business/mail/ru/mail-clients/others).
- Протокольный режим чтения: `EXAMINE` открывает папку без изменения постоянного состояния; `UID SEARCH`/`UID FETCH` работают с UID, `BODYSTRUCTURE` определяет MIME-части, `BODY.PEEK[...]` не ставит флаг прочитанности. Надежный идентификатор включает аккаунт, папку, `UIDVALIDITY`, `UID`; последовательные номера писем не подходят. При смене `UIDVALIDITY` старый UID-checkpoint инвалидируется и папка перечитывается. UID-checkpoint для новых писем не отслеживает все изменения флагов/удаления. [RFC 9051, §§2.3.1.1, 6.3.3, 6.4.4, 6.4.5, 6.4.9](https://www.rfc-editor.org/rfc/rfc9051.html).
- Получение текста технически возможно без обработки вложений: выбрать текстовые MIME-части, декодировать charset/Content-Transfer-Encoding; отдельные документы и изображения не анализировать. `BODY[TEXT]` всего письма само по себе не означает `text/plain`: multipart требует разбора структуры. [MIME: типы и multipart](https://www.rfc-editor.org/rfc/rfc2046.html), [MIME: кодирование](https://www.rfc-editor.org/rfc/rfc2045.html).

Не проверено: допускает ли конкретный учебный аккаунт ВШЭ IMAP и создание пароля приложения при своих административных настройках. Папки, правила отбора учебных писем и преобразование писем, содержащих только HTML, проверяются на примерах при реализации. Пароль приложения дает почтовый доступ; режим чтения сервиса обеспечивается его кодом, а не обещанием, что сам пароль имеет только read-only права.

## Google Calendar

- `calendars.insert` создает отдельный вторичный календарь; авторизованный пользователь становится владельцем. Google рекомендует авторизоваться как будущий владелец, а не создавать этот календарь от сервисного аккаунта. Метод допускает scope `calendar.app.created`. [Создание календаря](https://developers.google.com/workspace/calendar/api/v3/reference/calendars/insert).
- Расписание читается через `events.list(calendarId, ...)`; для чтения подходит `calendar.events.readonly`. Для записи в календарь, созданный приложением, методы событий допускают `calendar.app.created`: можно сочетать чтение расписания с правом управлять календарем приложения. Конкретные calendarId сохраняются отдельно. [Чтение событий](https://developers.google.com/workspace/calendar/api/v3/reference/events/list), [создание событий](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert), [изменение событий](https://developers.google.com/workspace/calendar/api/v3/reference/events/update), [удаление событий](https://developers.google.com/workspace/calendar/api/v3/reference/events/delete).
- Для синхронизации используется полный `events.list`, все страницы, затем `nextSyncToken` с последней страницы. Последующие запросы с `syncToken` возвращают изменения, включая удаления. При ответе `410 Gone` требуется новая полная синхронизация локальной проекции этого календаря. С `syncToken` нельзя передавать `timeMin`, `timeMax`, `updatedMin` и ряд других фильтров; остальные параметры должны сохраняться. Это исключает наивную схему «каждый раз новое временное окно + старый syncToken». [Синхронизация](https://developers.google.com/workspace/calendar/api/guides/sync), [ограничения events.list](https://developers.google.com/workspace/calendar/api/v3/reference/events/list).
- Повторяющиеся занятия, исключения и отмены представлены штатными полями `recurrence`, `recurringEventId`, `originalStartTime`, `status`. Изменения можно читать и из календаря расписания, и из календаря агента; API сам не выбирает приоритет ручного изменения пользователя и факта из учебного источника. [Ресурс Event](https://developers.google.com/workspace/calendar/api/v3/reference/events).
- Для постоянной работы VPS нужен OAuth-доступ пользователя с offline access и refresh token. Токены могут истечь/быть отозваны; обновление токена и восстановление авторизации — задачи сервиса. [OAuth для серверных приложений](https://developers.google.com/identity/protocols/oauth2/web-server#offline).

Не проверено: каким способом пользователь перенесет расписание HSE App X в Google Calendar и будет ли исходный календарь действительно обновляться. Google API синхронизирует доступный календарь, но не обеспечивает актуальность ручного импорта из другого приложения. Разрешение конфликтов ручных правок календаря остается отдельным правилом реализации, без переопределения продуктовой спецификации.

## Обычный Pi SDK

Проверен исходный репозиторий Pi на commit `4c6fb7cfe8c538a668726f6f8b3554098c39faee`; локальный checkout: `/tmp/hse-pi-memory-source`. Установка пакетов не выполнялась. Имена и сигнатуры относятся к этому commit, а не гарантированно к любому опубликованному npm-релизу.

- `createAgentSession(options)` из `@earendil-works/pi-coding-agent` предоставляет in-process TypeScript API, `session.prompt()`, подписку на события и `dispose()`. Поддерживаются `sessionManager`, `customTools`, `resourceLoader`, `tools`, `noTools`, `excludeTools`. [SDK](https://github.com/earendil-works/pi/blob/4c6fb7cfe8c538a668726f6f8b3554098c39faee/packages/coding-agent/docs/sdk.md).
- Постоянная сессия: `SessionManager.create(cwd, sessionDir?)`; восстановление конкретной сессии — `SessionManager.open(path, sessionDir?, cwdOverride?)`; также есть `continueRecent(cwd, sessionDir?)`. `createAgentSession` принимает этот manager. Для одного ассистента явный сохраненный путь обеспечивает восстановление именно его сессии. [SessionManager](https://github.com/earendil-works/pi/blob/4c6fb7cfe8c538a668726f6f8b3554098c39faee/packages/coding-agent/src/core/session-manager.ts), [пример сессий](https://github.com/earendil-works/pi/blob/4c6fb7cfe8c538a668726f6f8b3554098c39faee/packages/coding-agent/examples/sdk/11-sessions.ts).
- В этой версии `tools` — **массив имен**, не массив реализаций инструментов; реализации передаются через `customTools: ToolDefinition[]`. `noTools: "builtin"` подавляет исходное включение штатных инструментов и оставляет custom/extension tools; `tools: [...]` задает явный allowlist. `excludeTools` действует дополнительно. Поэтому одного «не включить bash по умолчанию» недостаточно для строгой конфигурации: сервис должен задавать allowlist только нужных учебных инструментов. [Сигнатуры SDK](https://github.com/earendil-works/pi/blob/4c6fb7cfe8c538a668726f6f8b3554098c39faee/packages/coding-agent/src/core/sdk.ts).
- Исходный код фильтрует встроенные и собственные инструменты по allowlist при сборке реестра. Однако загруженные extensions являются исполняемым кодом: `resourceLoader` должен контролироваться сервисом без автоматического обнаружения неизвестных extensions. Pi также имеет host API `executeBash`; сервис не должен выставлять его через команды/инструменты интерфейса. [AgentSession](https://github.com/earendil-works/pi/blob/4c6fb7cfe8c538a668726f6f8b3554098c39faee/packages/coding-agent/src/core/agent-session.ts), [пример полного управления ресурсами](https://github.com/earendil-works/pi/blob/4c6fb7cfe8c538a668726f6f8b3554098c39faee/packages/coding-agent/examples/sdk/12-full-control.ts).

Инженерное следствие: модель получает инструмент подготовки черновика и другие разрешенные учебные операции; фактическая отправка в чужой чат проходит только через сервисную проверку пользовательского одобрения. Allowlist ограничивает доступные модели инструменты, но не является песочницей для произвольного серверного кода и не заменяет эту проверку. На реализации следует зафиксировать версию Pi и проверить отсутствие `bash`/`read`/`write`/`edit` и иных путей отправки как в новой, так и в восстановленной сессии.

## Что остается проверить при подключении

1. Доступность выбранных Telegram-групп и истории с согласованной даты; получение правки после простоя; отправка ровно одобренного вопроса и привязка ответа.
2. IMAP учебного ящика, примеры MIME-писем, поведение checkpoint после перезапуска/смены UIDVALIDITY.
3. OAuth, реальные calendarId, перенос/отмена повторяющегося занятия, `syncToken` и восстановление после его инвалидирования.
4. Опубликованная версия Pi с проверенными SDK-сигнатурами; восстановление конкретной сессии и исполнение только разрешенных customTools.

Эти проверки требуют настройки конкретных аккаунтов и коротких интеграционных сценариев на этапе реализации. В этой записке они не объявлены пройденными.
