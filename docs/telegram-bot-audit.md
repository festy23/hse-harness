# Аудит Telegram Bot API

Независимый агент проверил исходный код целиком по
[telegram-bot-development](../.agents/skills/telegram-bot-development/SKILL.md)
и его [checklist](../.agents/skills/telegram-bot-development/references/review-checklist.md).
Исходная ревизия: `d480313`. Аудит выполнен 27 октября 2026 года.

## Найденные ошибки и исправления

1. Пересланный текст получал полномочия личного сообщения владельца, включая
   возможность менять статусы «сделал» и «сдал». Признак пересылки теперь сохраняется
   в очереди вместе с текстом и дедупликацией. Пересланные команды не исполняются,
   модель получает такой текст как данные с `ownerTurn=false`. Ответ владельцу сохраняется.
2. Ответ `429` терял `retry_after`. Адаптер теперь сохраняет общий срок паузы для
   Bot API в operations state. До его истечения повторные вызовы не обращаются
   к Telegram. Существующие циклы повторяют операцию после паузы; перезапуск её не сбрасывает.
3. Ответ `sendMessage` без корректного `message_id` мог отметить сообщение доставленным.
   Теперь проверяются JSON envelope и квитанция отправки. Неопределённый результат
   сохраняет состояние `sending`; повтор использует существующее предупреждение
   о возможной предыдущей доставке.
4. Ответ на callback ожидал выполнения медленных команд. Теперь он проходит
   отдельной ограниченной очередью; авторизация и порядок выполнения действий
   остаются в обработчике команд. Чужой callback получает ACK без выполнения действия.
5. Вложения и другие сообщения без текста молча подтверждались. Теперь владелец
   получает просьбу прислать задание текстом, с устойчивым идентификатором доставки.

Регрессии проверяют запрет ранних HTTP-запросов после 429 и перезапуска,
возобновление отправки после паузы, неполную квитанцию, сохранение происхождения,
пересланный `/ready`, полномочия модели, независимость callback ACK от медленной
команды, ограничение параллельных ACK, дедупликацию и отсутствие чужих действий.

## Что проверено

На дату аудита официальная документация публиковала **Bot API 10.3 от 24 августа
2026 года**. Проверены changelog после 9.6 и контракты используемых методов:
`sendMessage`, `getUpdates`, `answerCallbackQuery`, `getMe`; используемые параметры
совместимы. Bot API SDK в проекте отсутствует: основной транспорт — raw HTTPS
в `src/bot.ts`, проверка токена при настройке отдельно вызывает `getMe`.
`teleproto` обслуживает MTProto и не является Bot API SDK.

Проверены owner/private-chat авторизация, сохранение offset после завершения
префикса команд, дедупликация по bot identity/update ID, outbox, approval и
восстановление после сбоя, ограничение времени запросов, plain-text сообщения,
явные `allowed_updates`, active/drain lifecycle и локальная блокировка writer.
Неопределённая сетевая отправка может повториться: Bot API не предоставляет
идемпотентный ключ для `sendMessage`; предупреждение об этом сохраняется.

Webhook, платежей, Mini Apps и загрузки файлов через Bot API нет: соответствующие
пункты checklist неприменимы. Работа с группами здесь относится к отдельному MTProto-клиенту.

## Ограничения и дальнейшая работа

Реальный бот и секреты при аудите не использовались. Не проверены production
настройки BotFather/webhook, реальные 429/403, crash recovery в production и
шифрование диска ОС. Один токен должен обслуживать один активный poller;
локальная блокировка не защищает от другой установки с тем же токеном.

Постоянные ошибки 400/401/403 пока требуют лучшей классификации: сейчас
существующие очереди могут повторять их до устранения причины. Дополнительные
рекомендации: диагностика webhook-конфликта, регистрация команд через
`setMyCommands`, короткое стартовое меню, документированное удаление и сроки
хранения данных. Они не включены в исправления подтверждённых ошибок.
