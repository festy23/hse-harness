# Актуальные реализации памяти агентов

Дата среза: **3 октября 2026**, Москва. Исследование для учебного ассистента ВШЭ; это проверка механизмов, а не выбор архитектуры. Только первичные источники: документация разработчиков, код, релизы. У живой документации ниже обычно нет даты последнего изменения; датированные релизы подтверждают доступность реализации, но не автоматически всех описанных сегодня возможностей. Проверялись опубликованные GitHub releases, включая `published_at` через GitHub API; материалы позднее даты среза исключены.

## Letta: от блоков памяти к MemFS

Подтвержденный свежий релиз **Letta Code v0.34.2 — 2 октября 2026** уже содержит исправление локальных git-коммитов MemFS. У отдельного Python-сервера последний найденный релиз — **0.16.8, 14 мая 2026**; его предыдущий релиз 0.16.7, от 31 марта, явно описывает git memory sync и MemFS. Версии этих двух продуктов нельзя смешивать. [Code release](https://github.com/letta-ai/letta-code/releases/tag/v0.34.2), [Server releases](https://github.com/letta-ai/letta/releases).

В текущей документации MemFS — принадлежащий агенту git-репозиторий Markdown. Корневые файлы попадают в системный контекст; вложенные каталоги с индексами читаются по необходимости. Агент меняет их файловыми инструментами; коммиты дают историю версий, для cloud-агента push распространяет изменения между компьютерами. Встроенного векторного индекса по умолчанию нет: обычное чтение/поиск файлов, отдельная модификация добавляет keyword/semantic поиск. Git-конфликт — конфликт правок файла; это само по себе не проверка истинности двух противоречивых учебных фактов. Последнее — вывод по описанному механизму. [MemFS](https://docs.letta.com/concepts/memfs).

Dreaming запускает фоновых субагентов, которые просматривают разговоры и консолидируют уроки в память; возможен дополнительный проход проверки агентом, увеличивающий расход токенов. [Memory & dreaming](https://docs.letta.com/configuration/memory).

Текущая страница SDK считает V1 deprecated и описывает новый TypeScript Agent SDK с MemFS и self-hosting. Локальные агенты хранятся на диске и требуют собственных резервных копий; CLI требует Node.js 22.19+. Эти страницы не дают даты перехода SDK, поэтому нельзя утверждать точную дату появления всей новой API-поверхности. **Зрелость:** работающий опубликованный код и исправления есть; гарантии полноты извлечения дедлайнов не установлены. [SDK](https://docs.letta.com/v1-sdk), [Stateful agents](https://docs.letta.com/concepts/stateful-agents), [Quickstart](https://docs.letta.com/quickstart).

## Mem0: важно не описывать устаревший алгоритм

**Python SDK v2.2.1 — 25 сентября 2026.** Уже **14 апреля 2026** разработчики объявили переписанный ADD-only алгоритм: новые факты добавляются, а автоматическое извлечение больше не переписывает старые записи. Поэтому прежнее описание «LLM решает ADD/UPDATE/DELETE при каждом сообщении» не соответствует нынешней ветке. Явные `update`/`delete` сохраняются. [v2.2.1](https://github.com/mem0ai/mem0/releases/tag/v2.2.1), [датированный changelog](https://docs.mem0.ai/changelog/highlights).

`add` использует существующие релевантные воспоминания, извлекает факты LLM, дедуплицирует, создает embeddings и entity links. Обычная память — извлеченные факты, не полная стенограмма; `infer=False` сохраняет предоставленный текст. Platform объединяет vector/keyword/entity/temporal сигналы; OSS зависит от настроенного vector store и reranker. В текущем OSS внешний graph store убран; встроенный граф Platform нельзя приписывать self-hosted SDK. [Механизм](https://docs.mem0.ai/core-concepts/how-it-works), [OSS configuration](https://docs.mem0.ai/open-source/configuration).

**История обновлений реально есть:** в коде именно v2.2.1 имеются `history(memory_id)` и SQLiteManager с `old_memory`, `new_memory`, `event`, временными метками и признаком удаления. `_update_memory` меняет активную запись в vector store и добавляет старый/новый текст в историю. Это журнал изменений памяти; наличие журнала не означает автоматическую ссылку каждого извлеченного факта на исходное Telegram-сообщение. Такую связь нужно проверить или передать metadata. [main.py v2.2.1](https://raw.githubusercontent.com/mem0ai/mem0/v2.2.1/mem0/memory/main.py), [storage.py v2.2.1](https://raw.githubusercontent.com/mem0ai/mem0/v2.2.1/mem0/memory/storage.py).

Живая документация Platform Dream описывает отдельные supersede/merge с сохранением старых записей и synthesis паттернов в фоне; `latest_only=true` исключает устаревшие записи. Страница недатирована, появление всех этих возможностей к cutoff отдельно не подтверждено — это не доказательство наличия Dream в OSS. [Dream](https://docs.mem0.ai/platform/features/dream).

Self-host требует LLM, embedder и выбранное vector-хранилище; возможен локальный Qdrant, а серверный стек зависит от конфигурации. **Зрелость:** опубликованная поддерживаемая библиотека, но v2.2.1 только что исправил ложное сообщение об успешном ADD при отклонении записи vector store. Это свидетельство реального исправления, а не основание считать весь продукт ненадежным. [Configuration](https://docs.mem0.ai/open-source/configuration), [release](https://github.com/mem0ai/mem0/releases/tag/v2.2.1).

## Graphiti и Zep: временной граф с происхождением фактов

**Graphiti v0.30.2 — 8 сентября 2026.** В версионированном README описаны episodes с исходными данными, entities и fact edges. Новые episodes встраиваются постепенно; сущности и связи извлекаются и сопоставляются. Противоречащие старые факты инвалидируются, история сохраняется. Search соединяет embeddings, keyword search и обход графа; предусмотрены собственные типы сущностей/связей. [Release](https://github.com/getzep/graphiti/releases/tag/v0.30.2), [README v0.30.2](https://github.com/getzep/graphiti/blob/v0.30.2/README.md).

Bi-temporal модель различает время действительности факта и время его появления/обновления в системе. В коде есть `created_at`, `expired_at`, `valid_at`, `invalid_at` и ссылки `episodes` — можно проследить происхождение и смену версий. Это не гарантия правильного выбора между преподавателем и случайным ответом студента: авторитет источника и интерпретация срока требуют предметных правил. Последнее — вывод, а не заявленная функция Graphiti. [edges.py v0.30.2](https://github.com/getzep/graphiti/blob/v0.30.2/graphiti_core/edges.py).

Для self-host: Python 3.10+, LLM/embeddings и graph backend, например Neo4j или FalkorDB; у встроенного FalkorDB Lite требование Python 3.12+. Kuzu уже deprecated. Zep — отдельная managed-система поверх Graphiti с собственной инфраструктурой; ее SLA, governance и performance нельзя переносить на самостоятельное развертывание Graphiti. **Зрелость:** выпущенная библиотека с поддерживаемыми backends; заявленные production-свойства Zep и нагрузку на наш VPS экспериментально не проверяли. [README](https://github.com/getzep/graphiti/blob/v0.30.2/README.md), [Zep vs Graphiti](https://help.getzep.com/zep-vs-graphiti).

## Hindsight: retain, recall, reflect и фоновая консолидация

**v0.10.2 — 29 сентября 2026.** Датированный анонс Cloud от 21 сентября подтверждает доступность v0.10.0 и self-hosted реализации с изображениями/файлами в памяти; источники вложений могут вернуться вместе с извлеченными фактами. [Release](https://github.com/vectorize-io/hindsight/releases/tag/v0.10.2), [Cloud 0.10.0, 21.09.2026](https://hindsight.vectorize.io/blog/2026/09/21/hindsight-cloud-0-10-0).

`retain` извлекает датированные факты, связывает сущности; после завершения фоновая consolidation создает/обновляет observations со ссылками на подтверждающие факты. Mental models — отдельно заданные вопросы с сохраняемыми и обновляемыми ответами. Это три вида производных представлений, а не три независимых агента пользователя. [Retain](https://hindsight.vectorize.io/developer/retain), [Observations](https://hindsight.vectorize.io/developer/observations), [Mental models](https://hindsight.vectorize.io/developer/mental-models).

`recall` объединяет semantic, keyword, graph и temporal retrieval, затем reranking и ограничение токенами; можно запросить исходные chunks. `reflect` проводит дополнительные поиск/рассуждение и возвращает evidence в `based_on`. Временная фильтрация и evidence не доказывают исчерпывающий список заданий: retrieval ограничен кандидатами и бюджетом, а extraction вероятностный. Документация прямо предупреждает, что успешный retain иногда извлекает ноль фактов. [Retrieval](https://hindsight.vectorize.io/developer/retrieval), [Reflect](https://hindsight.vectorize.io/developer/reflect), [Retain](https://hindsight.vectorize.io/developer/retain).

Self-host: API, PostgreSQL как хранилище и очередь фоновых операций, LLM, embeddings/reranker; worker может работать внутри API или отдельно. **Зрелость:** релизы, код и опубликованные интеграции подтверждены; заявленное применение в крупных компаниях и лидерство бенчмарков — утверждения разработчиков, не наш независимый аудит. Нет измерения RAM/стоимости на VPS пользователя. [Services](https://hindsight.vectorize.io/developer/services), [официальный репозиторий](https://github.com/vectorize-io/hindsight).

## Mastra Observational Memory: новая практическая ветка

Датированный анонс **9 февраля 2026**, async buffering — changelog **11 февраля 2026**. Observer при превышении порога сообщений пишет датированные заметки; Reflector при росте заметок пересобирает сжатый журнал. Активный контекст — observations плюс еще не обработанные сообщения. Стабильный префикс рассчитан на prompt caching, vector/graph DB для этого механизма не нужны. [Анонс](https://mastra.ai/blog/observational-memory), [11.02.2026](https://mastra.ai/blog/changelog-2026-02-11).

Текущая документация показывает хранение через Mastra storage provider, например локальную LibSQL, и фоновую подготовку observations. Это LLM-компрессия с приоритетами, а не гарантированно без потерь сохраненный реестр дедлайнов. Из датированных источников не установлена обязательная связь каждой строки observations с исходным message ID или полноценная предметная обработка противоречий. **Зрелость:** есть открытая реализация и датированные исправления; рекламная точность LongMemEval не равна надежности Telegram-ассистента. [Документация](https://mastra.ai/docs/memory/observational-memory), [исправления 24.02.2026](https://mastra.ai/blog/changelog-2026-02-24).

## Что исследование пока не устанавливает

Сохранение состояния после перезапуска, извлечение/поиск памяти и точный запрос к состоянию приложения — разные задачи. Наличие диска, SQLite или очереди не определяет качество семантической памяти. Наличие temporal retrieval не подтверждает, что «все невыполненные задания до пятницы» возвращены полностью. Это технические выводы из описанных выше механизмов.

Ни бюджет **2000 ₽/месяц**, ни отсутствие пропусков не подтверждены для нашего объема сообщений. До выбора нужны одинаковые русские сценарии переноса/отмены/неопределенного срока, сохранения источников, переигрывания истории и перезапуска, плюс замер платных extraction/consolidation/reflect вызовов. Точные ежемесячные расходы без этих данных сейчас были бы предположением. Архитектура в этой заметке не выбирается.
