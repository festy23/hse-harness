# Проверки качества кода

`npm run check` запускает запрет комментариев, Oxlint, Oxfmt, TypeScript,
тесты проверок качества, тесты приложения и runtime. В GitHub Actions отдельная
задача `quality` выполняет статические проверки до Linux-матрицы и macOS.
Ошибка любой проверки останавливает CI. Обязательность статусов для merge
настраивается отдельно в правилах защиты ветки GitHub.

## Команды

- `npm run lint` — политика исходников и lint, включая анализ типов приложения.
- `npm run lint:fix` — безопасные автоматические исправления Oxlint.
- `npm run format` / `npm run format:check` — единый формат / проверка формата.
- `npm run typecheck` — строгие типы исходников и TypeScript-тестов без генерации файлов.
- `npm run test:quality` — проверка того, что ограничения действительно обнаруживают нарушения.
- `npm run check` — полный локальный набор; `npm run test:e2e` — сценарии интеграций и worker.

## Что запрещено

В собственных JS/TS/Python-исходниках, тестах и скриптах запрещены любые комментарии:
строчные, блочные, JSDoc, `@ts-ignore`, `@ts-expect-error`, `@ts-nocheck`,
`eslint-disable`, `oxlint-disable`. Пояснения хранятся в документации.
Проверка разбирает синтаксис через Oxc, поэтому URL, регулярные выражения и строки
с символами комментариев допустимы. Shebang исполняемого файла допустим: это
директива запуска, не комментарий JavaScript. Python-комментарии и docstring
проверяются стандартными `tokenize` и `ast`; для проверок нужен Python 3,
который также используется существующими CLI-тестами. Зависимости, сборка, данные,
документация и установленный сторонний скилл не проверяются как исходники приложения.

Oxlint запрещает явный `any`, `eval` и динамические конструкторы функций,
опасные конструкции Promise, небезопасный `finally`, недостижимый код,
нестрогие сравнения и циклы импортов. Блоки управления требуют фигурных скобок.
В `src/**/*.ts` дополнительно проверяются необработанные Promise (даже с `void`),
неправильное использование async-функций, операции с неявным `any`, полнота
`switch` по объединениям типов и глубина вложенности (максимум четыре блока).
Проверки выбраны явно в `.oxlintrc.json`, а не включены без разбора целыми категориями.

TypeScript использует `strict`, `noUncheckedIndexedAccess`, проверку возвратов,
явного `override`, неиспользуемых переменных и параметров, недостижимого кода
и проваливания веток `switch`. Эти настройки действуют и на TypeScript-тесты.
JavaScript runtime и скрипты проходят синтаксический lint и форматирование;
для JS/MJS/CJS также запрещены необъявленные имена и присваивание переменным `const`.
полная проверка типов JS не включена. Type-aware правила Oxlint относятся к `src`,
в тестах используются общие правила и строгий компилятор TypeScript.

Oxlint с `oxlint-tsgolint` выбран для установленного TypeScript 7. Версии инструментов
зафиксированы в `package.json` и lock-файле. Oxfmt задаёт одинаковое оформление
для всего собственного кода, поэтому первый запуск меняет много строк.

## Архитектура и безопасность

`src/domain.ts` не должен зависеть от транспорта, хранения, CLI или обновлений.
Запрет инфраструктурных модулей Node охватывает имена с `node:` и без него,
включая подпути вроде `fs/promises`.
Ограничения импортов и отсутствие циклов помогают сохранять направление зависимостей,
а лимит вложенности побуждает выделять отдельные операции. Это частичная автоматизация
архитектурных правил, а не доказательство соблюдения всех принципов SOLID.
Связность классов, ответственность модулей, подстановку реализаций и корректность
бизнес-правил по-прежнему проверяют тесты и ревью.

Внешние JSON-данные следует сначала принимать как `unknown`, затем проверять структуру.
`parseConfig` проверяет поля конфигурации до запуска интеграций: папки должны быть
массивом строк, интервал опроса — конечным числом в диапазоне таймера Node.
Пропущенный интервал равен 60 секундам; числовые значения ниже 15 поднимаются до 15.
Строки, `null` и переполнение таймера отклоняются, а не преобразуются в число.
Утверждение типа через `as` само по себе ничего не проверяет во время выполнения.
Lint не доказывает корректность схем ответов, авторизации, обработки секретов или
идемпотентности. Нельзя заменять такую проверку приведением типа ради зелёного CI.

При рефакторинге сохраняются инварианты доставки и восстановления:
payload outbox сохраняется до отправки, неоднозначный ответ не считается отказом,
курсор источника продвигается после сохранения результата, ошибка записи остаётся
фатальной, отмена дожидается завершения работы и освобождения ресурсов.
Compute worker выполняет только чистые преобразования: принудительное завершение
не должно прерывать внешнее действие. Эти свойства проверяют поведенческие тесты.
