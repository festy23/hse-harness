# Telegram-интерфейс обновления HSE HARNESS

Дата проверки: 18 октября 2026. Исследование официальных материалов Telegram и текущего кода HSE HARNESS 0.3.0. Production-код не менялся. Раздел «Рекомендации» содержит инженерные выводы для одного VPS; Telegram не предписывает архитектуру нашего установщика.

## Вывод

Для обновления из Telegram не требуется переходить на webhook, заводить второй бот, Kubernetes или сложный CI/CD. Достаточно сохранить существующий long polling и сделать Telegram командным интерфейсом к надёжной локальной операции обновления. Сам Telegram не скачивает npm-пакет и не перезапускает процесс: это задача установщика и системного менеджера сервиса.

Сейчас значительная часть интерфейса уже есть: проверка npm, предложение обновиться, подтверждение владельцем, сохранённый запрос, уведомления об исходе. Главная граница — обновление самого supervisor. Она относится к локальному управлению процессами, а не к выбору Telegram SDK или транспорта.

## Документированные свойства Telegram

### Приём команд и перезапуск

`getUpdates` и webhook взаимоисключаются. Telegram хранит необработанные updates максимум 24 часа. Вызов `getUpdates` с `offset > update_id` подтверждает update; ответ содержит до 100 записей. Положительный `timeout` включает long polling. После недели без updates следующий ID может быть выбран случайно. [Bot API: Getting updates, Update, getUpdates](https://core.telegram.org/bots/api#getting-updates).

Webhook доставляет HTTPS POST, повторяет неуспешные запросы, но документация не фиксирует число попыток. `secret_token` передаётся заголовком. `drop_pending_updates` удаляет ожидающие updates. [setWebhook](https://core.telegram.org/bots/api#setwebhook), [deleteWebhook](https://core.telegram.org/bots/api#deletewebhook).

В официальном сервере новый параллельный `getUpdates` отменяет предыдущий ожидающий запрос с HTTP 409 и диагностикой о нескольких экземплярах. [Исходники Client::abort_long_poll](https://github.com/tdlib/telegram-bot-api/blob/master/telegram-bot-api/Client.cpp).

### Кнопки и ответы

`callback_data` вмещает 1–64 байта; callback содержит отправителя. Telegram предупреждает, что данные callback не следует считать доказательством наличия соответствующей кнопки. Для остановки индикатора ожидания необходим `answerCallbackQuery`. При flood control `retry_after` задаёт задержку повтора. [InlineKeyboardButton](https://core.telegram.org/bots/api#inlinekeyboardbutton), [CallbackQuery](https://core.telegram.org/bots/api#callbackquery), [ResponseParameters](https://core.telegram.org/bots/api#responseparameters).

Область видимости меню команд не заменяет проверку полномочий на сервере. Telegram рекомендует менять клавиатуру существующего сообщения при изменении состояния. [Command scopes и Inline keyboards](https://core.telegram.org/bots/features#command-scopes).

FAQ советует избегать отправки более одного сообщения в секунду в один чат. [Bots FAQ: limits](https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this).

### Особенность официальных источников

В FAQ формулировка границы подтверждения offset менее точна, чем в справочнике Bot API: рядом с примером `last processed + 1` сказано «less than or equal to offset». Для реализации следует использовать строгое правило основного справочника: подтверждаются ID, **меньшие** offset. Не следует переносить неточную фразу FAQ в тесты.

Официальные страницы обновляются независимо: общий FAQ содержит устаревающие обобщения о возможностях ботов. Поэтому исследование использует справочник конкретного метода для контракта, а FAQ — только для рекомендаций по нагрузке. Текущая открытая страница API отмечает Bot API 10.3 от 24 августа 2026; для предлагаемого интерфейса достаточно давно существующих методов, без миграции на новые виды кнопок.

## Что уже реализовано в HSE HARNESS

Ниже — наблюдения по локальному исходному коду, а не обещания Telegram.

| Место | Фактическое поведение | Последствие для развития |
|---|---|---|
| `src/bot.ts` | Long polling 25 секунд, HTTP-запрос ограничен 40 секундами, получаем `message` и `callback_query` | Транспорт подходит для одного VPS; смена его не нужна для самообновления |
| `src/bot.ts:isOwner()` | Сопоставляются числовой ID отправителя, ID личного чата и тип `private` | Сохранять одинаковую проверку у команды, callback и переключателей политики |
| `src/worker/commands.ts` | Окно до 100 updates, отдельные быстрые команды, offset продвигается через завершённый префикс после сохранения | Перезапуск обновления должен сохранять этот контракт и завершать принятые операции |
| `src/bot.ts:sendChunks()` | Долговечный outbox, фиксированный payload, `message_id` после ответа; потерянный ответ оставляет неоднозначность | Продолжать использовать эту систему для уведомлений обновления; не обещать абсолютное отсутствие дублей |
| `src/updates/telegram.ts` | Проверка latest примерно каждый час; обычное предложение не чаще раза в 24 часа; `/updates` проверяет вручную | Интерфейс «узнать версию и предложить обновить» уже существует |
| `src/updates/telegram.ts:callback()` | Случайный offer ID; сверка версии и integrity; защита от устаревшей кнопки и уже активного запроса; запрос сохраняется до grant | Расширять существующую операцию, не создавать отдельный обходной запуск npm из обработчика |
| `src/main.ts` | Callback подтверждается через `ack()` перед выполнением действия | Есть правильная отдельная стадия UI-подтверждения, но она сейчас ждёт места в последовательной очереди |
| `runtime/supervisor.mjs` | Уведомления сохраняются и передаются активному worker; сообщения об успехе после commit, об откате после восстановления | Сохранять одного отправителя; supervisor не должен становиться вторым poller |

Отдельный технический пробел: `BotApiRejection` сейчас сохраняет текст ошибки, но не типизированные `error_code` и `parameters.retry_after`. По прочитанным файлам нет общего планировщика исходящих сообщений с соблюдением этой задержки. Для обновлений это небольшая нагрузка, но смесь сводок, ошибок и прогресса может вызвать ограничение одного чата.

## Рекомендации для одного VPS

### Сохранить long polling

Это проектная рекомендация по стоимости эксплуатации: исходящие HTTPS-запросы уже работают через настроенный прокси, а публичный HTTPS endpoint и сертификат добавили бы обязанности без решения проблемы обновления supervisor. Официальный [webhook guide](https://core.telegram.org/bots/webhooks) отдельно описывает входящие подключения и TLS; webhook — допустимая альтернатива при других требованиях к размещению, а не обязательный «production mode».

При переключении версии сначала остановить старый polling, завершить и сохранить уже принятые действия, затем передать единоличное владение новому процессу. Подготовка кандидата может идти параллельно, но он не должен читать реальные updates и отправлять сообщения до активации. Supervisor/updater тоже не запускает `getUpdates`. Это сохраняет существующую модель единственного писателя.

Webhook, если когда-нибудь появится другая причина для перехода, потребует быстрой долговечной приёмки и дедупликации до HTTP 2xx. Он сам по себе не обеспечивает ни готовности новой версии, ни ровно однократного эффекта, ни безопасного отката. Во время обычного обновления нельзя включать `drop_pending_updates` или использовать отрицательный offset как способ «начать с чистого листа».

### Команда и кнопка должны запускать одну операцию

Предлагаемый UX: `/updates` показывает работающую версию, доступную версию, краткую информацию и кнопки «Обновить» и «Напомнить завтра». Текст явно сообщает о короткой паузе в ответах, если требуется перезапуск всего сервиса. Подтверждение привязывается к конкретным версии, integrity и offer ID; версия не подменяется незаметно после согласия.

Нажатие быстро закрывает индикатор ожидания отдельным коротким `answerCallbackQuery`, а затем получает долговечное сообщение «Запрос принят». Это разные подтверждения: первое обслуживает UI Telegram и не доказывает сохранение операции или начало установки. Желательно не держать callback ACK за медленной командой календаря; отдельная лёгкая стадия после проверки владельца может отвечать «Принято, ожидает очереди». Не надо ждать окончания npm в HTTP-ответе на callback.

Повторное нажатие, повторная доставка update и старая кнопка не создают новый install. Бот сообщает существующий request ID/текущую фазу. После принятия предложения клавиатуру можно убрать или заменить состоянием «Обновляется», но защита остаётся в серверном состоянии: изменение кнопки — лишь удобство интерфейса.

Авторизация операции остаётся детерминированной: числовой owner ID и личный чат. Текст модели, пересланное сообщение, имя пользователя или наличие команды в меню не дают разрешения устанавливать пакет. Кнопка содержит непривилегированный идентификатор, а не shell-команду, токен или произвольный URL архива.

### Два режима без сложного CI/CD

1. **Предлагать обновление — режим по умолчанию.** Проверять опубликованный stable latest по расписанию; уведомлять об одной доступной версии не чаще раза в сутки. Владелец нажимает кнопку. Недоступность npm не влияет на обычные команды бота. Сохранить ручной `/updates`.
2. **Автоматически обновлять — явно включаемая политика.** Пользователь заранее разрешает совместимые обновления; бот сообщает начало и итог. Тихое окно и пауза автоматических обновлений — настройки политики, а не дополнительные сервисы. Рискованные переходы или неизвестная совместимость остаются на подтверждении.

Периодичность проверок и предложение «раз в сутки» — продуктовый выбор HSE HARNESS, не лимит Telegram. Не нужно создавать отдельный GitHub webhook или CI/CD для обнаружения нового npm latest: это может выполнять существующий локальный цикл. Независимый локальный updater для supervisor исследуется отдельно; транспорт команд одинаков для обоих режимов.

### Уведомления должны переживать обновление

Минимальная последовательность: обнаружено → принято владельцем/политикой → подготовлено → ожидает завершения операций → переключается → новая версия проверена либо прежняя восстановлена. Каждая внешняя операция имеет устойчивый ID; финальный текст формируется из реально работающей версии и результата проверки, не из успешного `npm install`.

Запись о результате должна находиться вне каталога заменяемого релиза. Если бот временно недоступен, новый или восстановленный worker отправляет итог после восстановления. Повторные попытки следуют outbox и backoff; `retry_after` следует сохранять как структурированные данные. Прогресс лучше редактировать в одном сообщении или отправлять только при переходе значимых стадий. Ежесекундные «ещё устанавливаю» пользователю не нужны.

При потере ответа `sendMessage` невозможно по одному локальному факту понять, увидел ли пользователь сообщение. Наш outbox уже правильно показывает такую неоднозначность. При недоступной сети или блокировке бота владельцем обещание мгновенного итогового уведомления невыполнимо. В случае полного отказа сервиса необходим внешний способ восстановления — хотя бы SSH/systemd; Telegram-команда не работает, если некому её принять.

## Проверки перед обещанием «обновление одной кнопкой»

- Два одновременных poller с одним токеном: только активный процесс владеет приёмом; конфликт диагностируется.
- Перезапуск между принятием callback, сохранением request и продвижением offset: повтор не создаёт вторую установку.
- Двойное нажатие и устаревшее предложение: сохраняются exact версия и integrity либо требуется новое согласие.
- Медленная команда перед callback: UI получает быстрый ACK, операция не теряется из очереди.
- Перезапуск во время отправки уведомления: неоднозначность видна, payload и delivery ID сохраняются.
- Отказ npm, Telegram/proxy и 429: обычная работа продолжается, исход обновления не подменяется успехом уведомления.
- Успешная установка, но неуспешный запуск: пользователь получает результат отката после восстановления.
- Длительный простой: система не обещает восстановить через Bot API updates, срок хранения которых уже истёк.

Эти проверки — рекомендации к будущей спецификации; в рамках данного исследования они не выполнялись против живого бота.

## Обещания, которых следует избегать

- «Telegram сам обновляет приложение» — Telegram только доставляет команды и сообщения.
- «Webhook обязателен для production и решит обновление» — это другой транспорт, не установщик.
- «Можно держать две версии с одинаковым токеном активными» — подготовка кандидата и активный polling должны различаться.
- «После ACK обновление точно запущено» — UI ACK, долговечная приёмка и начало установки имеют разный смысл.
- «Ни одно сообщение никогда не потеряется» — есть предел хранения Telegram и необходимость долговечного локального подтверждения.
- «Дублей сообщений гарантированно не бывает» — потеря ответа внешней отправки оставляет неопределённость.
- «Бот всегда сам сообщит об аварии» — полностью остановленный сервис или недоступный Telegram не могут этого сделать.
- «Кнопка уже обновляет любую часть приложения» — для текущего supervisor это ещё нужно разработать и проверить.
