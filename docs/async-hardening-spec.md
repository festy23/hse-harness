# Устойчивое асинхронное выполнение HSE HARNESS

Реализация основана на рабочем состоянии 0.2.3, включая IMAP fix. Базовый
снимок в отдельной ветке: `3ade71e`. Исходный пользовательский checkout,
учётные данные и работающий VPS не изменяются. Этот документ описывает
поведение реализации, ограничения и проверку; публикация пакета — отдельный шаг.

## Границы и совместимость

- Node.js >=22.19; существующий Pi 1.0.2 и его JSONL остаются единственным
  механизмом разговорной памяти. Модельные запросы последовательны.
- IPC protocol 1, runtime schema 1, operations schema 2 сохранены.
- `async` не заменяет CPU-изоляцию. Небольшие проверки и хеши остаются синхронными.
- Сетевая недоступность не равна сломанному выпуску. Ошибки долговечности и
  инвариантов завершают worker контролируемо, а не скрываются как сбой провайдера.
- Принятый prompt не прерывается автоматическим drain. Источники используют
  отдельный сигнал, который не отменяет принятые инструменты и согласованные отправки.

## Контекст и бюджеты

`OperationContext` содержит ID, тип, сигнал, монотонный deadline,
`remainingMs()` и `throwIfAborted()`. Вложенный запрос получает минимум своего
бюджета и остатка родителя. Слушатели и таймеры удаляются в `finally`.
`withOperation` ждёт реальное завершение/очистку; истечение deadline не
освобождает право на внешнюю запись через один `Promise.race`.

| Граница | Бюджет |
|---|---:|
| Telegram RPC | 30 секунд с внутренними повторами |
| Telegram connect/discovery | 120 секунд |
| Telegram history work slice | 60 секунд после подключения |
| Чтение истории / вопрос | 45 секунд |
| Добавление чата | 120 секунд |
| IMAP порция / текст одного письма | 120 / 45 секунд |
| HTTP календаря / полный снимок | 30 / 120 секунд |
| Календарная мутация | 90 секунд |
| HSE с redirects и body | 45 секунд |
| Закрытие клиента | 5 секунд до закрытия ресурса |
| Чистая вычислительная задача | 30 секунд |

Пятиминутный network-idle timeout Pi сохранён; общего нового prompt deadline нет.
Ожидание человека в CLI не входит в бюджет сетевой фазы авторизации.
Нельзя гарантировать прерывание синхронного кода или зависшего системного вызова
таймером Node.js. Отдельные cleanup/refresh операции ждут безопасного завершения.

## Независимые контуры

Bot polling, Telegram, IMAP, календарь, инициализация/очередь Pi, локальные
напоминания, восстановления подтверждений и календарные записи выполняются
отдельными зарегистрированными lifecycle операциями. На источник приходится
один опрос. Конструирование календаря не выполняет сетевого discovery.

Для каждого источника `/status` показывает первоначальную готовность,
продолжение порции, последний успех и тип/время последнего сбоя без секретов. Метаданные хранятся в namespaced
курсорах; после старта первоначальная сверка проверяется заново. `/ready`
требует сверки выбранных источников и пустой очереди.

Сбой старого approval не блокирует запуск. Recovery обрабатывает четыре
разных операции одновременно и собирает ошибки после завершения остальных.
При отзыве разрешения дальнейший повтор прекращается, payload и random ID
сохраняются, владелец предупреждается о возможном неизвестном прошлом исходе.
Неоднозначная отправка сохраняет `sending` и прежний `random_id`.

Календарные изменения и отправки напоминаний сериализуются по task ID.
Refresh фиксирует эпохи и версии операций перед сетью; устаревший снимок не
возвращает прежние jobs поверх нового намерения. Неопределённые PUT не
повторяются вслепую; marker `writeAttempted` опционален в существующей schema 2.
Ожидающее проверки задание получает одно устойчивое уведомление; другие задания
продолжают обслуживаться. Подтверждение фактического desired состояния снимает
неопределённость. Удалённое ручное исправление при неизвестном исходе требует
проверки пользователя, а не выдуманного успешного результата.

## Команды и подтверждение updates

Polling не ожидает обработчик или доставку его ответа. Быстрая очередь имеет
два слота (`/help`, `/status`), медленная —
одного исполнителя и максимум 32 принятых операции. Принятые ожидающие задачи
учитываются lifecycle сразу и вправе завершиться во время drain.

В памяти удерживаются до 100 наблюдаемых updates со статусами waiting/running/done.
Offset продвигается только через завершённый префикс **наблюдаемых** ID;
числовые пропуски разрешены, waiting overflow остаётся барьером. `enqueueOwner`
сохраняет очередь и receipt, но не меняет offset. Все командные ответы имеют
устойчивые delivery ID. После сбоя незавершённые updates доставляются повторно;
внешние действия защищают прежние approvals/update/task журналы.
Изменения здоровья подсистем также сохраняют уведомление с delivery ID до отправки;
polling не ждёт доставки служебной ошибки или сообщения о восстановлении.

При закреплённом полном окне update101 недоступен по правилам Bot API.
Повторное чтение одного окна выдерживает минимум секунду, не создавая tight loop.
Bot API сохраняет updates ограниченное время; этот механизм не является архивом.

## Сеть и продолжение истории

- Telegram использует raw ограниченные RPC вместо неотменяемых SDK-итераторов.
  Пагинация сохраняет pinned/peer offsets и проверяет повтор страницы.
- Параллельные потребители разделяют одну попытку подключения. Отмена одного
  ожидания не отменяет другого; последний отменившийся ждёт cleanup попытки.
  Публикация устаревшего поколения клиента запрещена.
- После исчерпания SDK-reconnect используются повторы 1/5/15/60 секунд.
  Ошибка auth блокирует сеть до изменения сохранённой сессии. FLOOD_WAIT
  откладывает конкретный RPC, не удерживая общий sleep или другой тип запроса.
- Страницы истории сохраняются до offset продолжения. Отсутствующие сообщения
  считаются удалёнными только после полного сканирования. Полная resync фиксирует
  исходный watermark и завершённые чаты через slices; новое сообщение после
  watermark подбирается последующим difference.
- В IMAP отмена закрывает клиент. Недочитанное/слишком большое письмо не
  продвигает UID. Обработчик позднего error сохраняется на время жизни клиента.
- CalDAV/Google передают сигнал через discovery, страницы и записи. При отмене
  неполного снимка сохраняются прежние token и snapshot, без ложных отмен.
- Любой неоднозначный send/PUT допускает фактическое исполнение на сервере;
  локальная отмена не доказывает отсутствие эффекта.

## CPU и долговечность

- Московский formatter кэшируется. Поиск по оригинальным Pi entries идёт назад
  до восьми совпадений, возвращает прежний порядок и уступает event loop каждые
  ~5мс через macrotask. Восстановление результата операции также кооперативно.
- Enqueue вычисляет fingerprint один раз, готовит большие chunks порциями и
  атомарно публикует seen вместе с очередью до сохранения.
- Store объединяет ожидающие сохранения: одна активная запись и одна ожидающая
  группа ревизий. Promise разрешается только после покрывающего fsync/rename/
  directory-fsync. Ошибка writer остаётся fatal для следующих save и flush.
- Чистый CPU worker обрабатывает HTML и ICS/повторения: одна активная задача,
  очередь до восьми, 30с, лимит heap 256 МиБ. У него нет API внешних эффектов.
  Отменённая активная вычислительная задача завершается вместе с worker до
  разрешения родительского promise.
- Лимиты: HSE — 1 МБ, HTTP календаря — 8 МиБ, ICS — 2 МиБ, до 20 000 раскрытых экземпляров.
  Превышение — явная ошибка, без усечения, ложных удалений или движения cursor.
- Не очищать receipts и историю ради performance. Синхронные Pi SDK persistence/
  load/auth, XML tsdav и одна JSON-сериализация полного состояния остаются
  измеряемыми ограничениями. Отдельный процесс Pi не введён.

## Supervisor и установка

Supervisor 1.0.1 наблюдает worker, пока отдельная подготовка immutable release
ещё выполняется. Завершение подготовки только записывает outcome; переключение
начинает один основной автомат после повторной проверки настроек и identity.
Disable/version change/manual action/stop отменяет подготовку и ждёт cleanup.
Живой worker не уничтожается ради обновления; старые drain/rollback бюджеты
сохраняются. IPC write/rejection направляются в штатное fatal завершение.
Повтор старой команды drain не может отменить новые контексты источников.
Потерянный activation ACK не доказывает неактивность кандидата. После отправки
activate его остановка при обновлении требует drain и подтверждённого quiescent;
при задержке принятой операции откат откладывается с сохранением ownership.
CLI после отмены ждёт settlement исходного SDK-вызова перед откатом credentials;
поздний запрос SDK на ввод телефона уже не открывает новый prompt.

Установщик выбирает engine из проверенного **установленного** выпуска отдельно
от сохранённого active worker. Hold/quarantine/previous/attempt не сбрасываются.
Manifest допускает стабильный minimum supervisor <= установленного; protocol и
форматы всё равно проверяются. Новые manifests получают minimum 1.0.1.

Обновление самого engine — обслуживаемая операция: дождаться безопасного
завершения текущей работы, остановить сервис, установить согласованную новую
версию npm, повторить `hse-harness service install`, проверить
`hse-harness updates status` и `/status`. Существующие proxy drop-ins сохранить.
Простой restart старого launcher не устанавливает новый engine. Обычные
следующие worker updates продолжают прежний механизм. Номер публикуемого
пакета выбирается при отдельном выпуске; повторно публиковать 0.2.3 нельзя.

## Проверка

```
npm run check
npm run test:e2e
npm run test:e2e:managed
npm run test:updates
npm run test:package
npm run benchmark:async
```

`npm test` сначала компилирует реальный CPU worker. Проверки используют
синтетические и loopback fixtures, без реальных аккаунтов.

Обязательные регрессии: зависший RPC, terminal reconnect, отмена одного waiter,
частичная многочатовая resync, неизвестный send и PUT, IMAP trickle timeout,
ошибочный исторический approval, независимые напоминания, stale calendar refresh,
медленная команда/доставка, sparse update IDs/overflow, падение между эффектом и
offset, drain с принятой очередью, stale drain, IPC failure, смерть worker во
время подготовки, поздняя отменённая подготовка и serviced engine upgrade.

Benchmark сообщает host/Node, elapsed, p95/max timer gap: 10k Pi entries,
50 МиБ состояния со 100 save barriers, HTML около 1 МБ, частые recurrence.
Цель выделенной среды — p95<=50мс, max<=250мс; общий CI проверяет реальный прогресс
таймеров, а не жёсткую скорость общей виртуальной машины. `/status` добавляет
p95/max event-loop delay, возраст операций и source progress. Heartbeat доказывает
жизнь процесса, но не успешность источников. Результаты локального Mac не
являются замерами VPS.

## Локальный результат benchmark, 17 октября 2026

[Исходные измерения и характеристики машины](benchmarks/async-hardening-2026-10-17.jsonl).
Это Mac Apple M3, 16 ГиБ, Node 26.5.0. Node 22, Linux и systemd в этом локальном
прогоне не проверялись; для них настроен CI.

| Нагрузка | p95 timer gap | Максимальный timer gap |
|---|---:|---:|
| Поиск по 10 000 оригинальным entries | 6,18 мс | 10,36 мс |
| Snapshot состояния 50 МиБ, 100 save barriers | 65,12 мс | 65,12 мс |
| HTML 999 026 байт в worker | 1,20 мс | 5,78 мс |
| 14 700 календарных экземпляров в worker | 1,32 мс | 1,67 мс |

Snapshot benchmark использует асинхронный sink в памяти: он измеряет сериализацию
и объединение сохранений, без дисковой пропускной способности. Реальные write,
file fsync, rename и directory fsync проверяются отдельными тестами с отказами.
Сотня одновременных save объединена в один snapshot.

Локальный p95 для snapshot **выше цели 50 мс**: одна полная JSON-сериализация
остаётся синхронной, как предусмотрено ограничениями первой версии. Эти цифры
не подтверждают выполнение performance SLO на выделенной среде. Максимум
измеренной задержки ниже 250 мс. CI сохраняет benchmark с характеристиками
runner как artifact; проверки прогресса таймеров входят в обычные тесты.

## Проверка итогового кода

Локальный `npm run check`: **219 тестов приложения и 61 тест runtime**, без
ошибок; компиляция и typecheck прошли. Обычные E2E: **40 сценариев** для iCloud,
Google, Яндекса и старта с недоступными подключениями. Managed E2E:
**14 сценариев**, включая drain во время настоящего Pi prompt и повторный
запуск с той же JSONL-памятью.

Тесты также проверяют потерянный activation ACK, отсутствие принудительной
остановки принятой операции и поздние SDK callbacks при отмене CLI.
Пакет и VPS этим изменением не публикуются и не обновляются.

`npm run test:updates` проверил два полных npm-архива с настоящими зависимостями:
процесс supervisor сохранился, память и очередь сохранились, измеренная пауза
переключения составила 6,715 с при тестовом пределе 15 с.

`npm run test:package` прошёл на итоговом коде: архив устанавливается без
dev-зависимостей, CLI работает, профиль сохраняется вне package root,
собранный daemon проходит E2E из установленного пакета и корректно останавливается.
