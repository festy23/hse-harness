# Память в Pi и Personal Study Assistant

Проверено 3 октября 2026 года по официальной документации и исходникам. **Обновление решения от 4 октября:** пользователь выбрал только штатную память Pi Agent для начального этапа — сессии и compaction. Предложения о дополнительных слоях ниже сохранены как история исследования и не применяются к текущей реализации. Актуальное решение — в [спецификации](../specification.md).

## Что уже есть в Pi

Официальный адрес `badlogic/pi-mono` перенаправляет на [earendil-works/pi](https://github.com/earendil-works/pi). Это актуальный upstream. Для проверки исходников прочитан commit `4c6fb7cfe8c538a668726f6f8b3554098c39faee`.

### Pi coding agent

- Диалог сохраняется автоматически. По умолчанию сессии находятся в `~/.pi/agent/sessions/`, сгруппированные по рабочей директории. Есть продолжение последней сессии, выбор существующей сессии и режим без сохранения. [Sessions and Context](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sessions.md)
- История — JSONL-дерево с ID и ссылками на родительские записи. В контекст модели попадает активная ветка. Сохранение полной истории не означает, что модель видит ее целиком в каждом запросе. [How Pi Works](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/how-pi-works.md), [Session Format](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/session-format.md)
- Compaction генерирует резюме старой части разговора и оставляет недавние сообщения; оригинальные записи сохраняются. Это сжатие контекста, а не структурированная база обязательств. [Compaction](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/compaction.md)
- `AGENTS.md` загружается из глобального каталога, родительских директорий и рабочей директории; `SYSTEM.md` и `APPEND_SYSTEM.md` управляют системными инструкциями. Расширения могут добавлять контекст, реализовывать RAG и долгосрочную память. Последнее описано как возможность разработки расширения. [Официальный сайт, Context engineering](https://pi.dev/#context-engineering)
- SDK позволяет встроить Pi в Node.js/Bun и предоставить свои инструменты и загрузчик ресурсов. `SessionManager` отвечает за сохраненную историю; простая замена `agent.state.messages` ее не заменяет. [SDK](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sdk.md)
- Документация расширений разделяет состояние инструментов, дополнительные записи сессии и внешние данные. Для данных за пределами одной сессии прямо рекомендует внешнее хранилище. [Extensions, State](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md#persist-state)

### Новое: Pi Durable

1 октября 2026 года вместе с Pi 1.0 выпущен отдельный **экспериментальный** `@earendil-works/pi-durable`. Он предназначен для длительно работающих приложений и не заменяет coding agent. [Официальный анонс](https://earendil.com/posts/pi-durable/), [Changelog](https://github.com/earendil-works/pi/blob/main/packages/durable/CHANGELOG.md)

В нем уже реализованы сохраняемые диалоги и задачи, восстановление после перезапуска, SQLite/JSONL-хранилища, атомарные изменения записей и собственных типизированных JSON-документов приложения. Такие документы подходят как технический механизм хранения нашего состояния, но предметы, задания, дедлайны и правила их обновления придется определить самостоятельно. Есть compaction; старая история сохраняется. `MemoryStorage` ничего не сохраняет на диск. API явно помечен как меняющийся без предупреждения между релизами. Хранилищем владеет один процесс, блокировок между процессами нет. [README Pi Durable](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md)

SQLite-адаптер использует WAL и `synchronous = NORMAL`: документация различает восстановление при падении процесса и возможную потерю новейших изменений при сбое питания/хоста. Это не обещание абсолютной неуязвимости данных; резервирование остается задачей приложения. [SQLite adapter](https://github.com/earendil-works/pi/blob/main/packages/durable/src/storage/sqlite/node.ts)

## Чего не следует обещать как готовую функцию

В проверенных стандартных coding-agent/agent-core/durable исходниках и документации нет готового компонента, который автоматически ведет долгосрочную семантическую память о студенте, извлекает обязательства из Telegram, согласует конфликтующие дедлайны и строит базу знаний по предметам. Проверка включала SDK, SessionManager, расширения, экспортируемые API Durable и поиск реализации semantic/vector/embedding/retrieval. Встроенный поиск инструментов относится к выбору инструмента, а не к памяти фактов. Сторонние пакеты не исследованы; этот вывод относится к проверенному стандартному upstream.

Наличие `defineDoc`, SQL-хранилища и примеров todo не равно готовой учебной модели памяти. Полнотекстовый или векторный поиск также сам по себе не определяет, какой срок актуален и кому он относится.

## Предлагаемая граница памяти — вывод для нашего проекта

Рекомендую четыре слоя:

1. **Рабочий контекст Pi:** текущий разговор, недавние сообщения, резюме. Это помогает рассуждать и поддерживать диалог.
2. **Постоянное состояние учебы:** предметы, задания, точные/неизвестные сроки, подтвержденность, актуальные версии, источники, статус выполнения, запланированные и отправленные уведомления. Сначала разумно рассмотреть SQLite на VPS; конкретный runtime и схема еще открыты.
3. **Архив доказательств и база знаний:** исходные сообщения и их изменения, версии страниц/ПУД, формулы накопа и условия оценивания с учебным годом и ссылками. Сначала достаточно фильтров и текстового поиска; семантический поиск добавлять по доказанной необходимости.
4. **Профиль пользователя:** программа и учебный год, группа, выбранные предметы, настройки уведомлений и явно подтвержденные предпочтения. Профиль доступен независимо от смены сессии.

Дедлайн должен существовать как проверяемая запись вне резюме диалога. Напоминания выбираются из постоянного состояния программно, даже после очистки контекста, смены модели и перезапуска. LLM извлекает и объясняет информацию; правила изменения состояния и планировщик определяют, что сохранить и когда уведомить. При неизвестном сроке сохраняется неопределенность и задача уточнения.

Для MVP предлагается сравнить coding-agent SDK плюс собственное хранилище с Pi Durable. Экспериментальный статус Durable требует отдельной проверки восстановления, обновления версии и доставки уведомлений; сегодня это кандидат, а не выбранная зависимость.
