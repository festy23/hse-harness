# Автоматическое применение обновлений HSE HARNESS

Дата: 13 октября 2026 года. Статус: `@ivan-boss/hse-harness@0.2.0` опубликован в npm с меткой latest. Реализация проверена локально и в CI на Linux/macOS; проверки и ограничения описаны ниже. Переход с 0.1.0 требует одной первоначальной остановки.

Пользователь хочет обновлять установленный пакет через `npm update -g @ivan-boss/hse-harness`, после чего бот должен самостоятельно перейти на новую версию без ручных `service stop` и `service restart`. При переключении разрешена короткая пауза обработки. Полностью непрерывная работа нескольких экземпляров не требуется.

Этот документ определяет реализацию. Исследования: [жизненный цикл приложения](research/update-runtime.md), [npm, Node и systemd](research/update-platform.md), [сбои и проверки](research/update-failures.md). Общие учебные требования остаются в [спецификации продукта](specification.md).

Численные настройки и правила данного документа имеют приоритет над альтернативными предложениями в исследованиях. Это выбранный дизайн для реализации; исследования не являются отчётом о прошедшей приёмке режима.

## 1. Контракт режима

- После первоначального включения управляемый бот автоматически замечает новую **установленную** версию и готовит её запуск. Самостоятельное скачивание любых следующих `latest` без команды пользователя не входит в режим.
- Обычная команда пользователя: `npm update -g @ivan-boss/hse-harness`. `npm install -g @ivan-boss/hse-harness@latest` тоже является допустимым сигналом.
- Старый бот продолжает работу во время загрузки и проверки кандидата. Для переключения он завершает уже начатые операции, сохраняет состояние и освобождает подключения. Затем начинает работу новая версия.
- Если подготовка не удалась, текущая версия продолжает работу. Если новая версия не запускается, управляющий процесс возвращает предыдущий совместимый выпуск.
- Подписочный вход, выбранные чаты, календари, Pi JSONL, очередь и отметки доставки сохраняются. Повторное одобрение ранее одобренного вопроса не появляется из-за штатного обновления.
- Только один рабочий процесс одновременно владеет учебным состоянием и подключениями. Управляющий процесс не вызывает Pi и не выполняет учебные инструменты.
- CLI и Telegram показывают фактически работающую версию отдельно от версии глобального npm-пакета. После отката они могут различаться.

**Граница гарантии:** наблюдатель не получает код завершения чужой команды `npm update`. Поэтому событие означает «обнаружена новая установленная версия, её отдельная установка и проверки завершились успешно», а не «доказан успешный выход исходного npm-процесса». Это ограничение должно быть в справке. Повторное чтение установленной версии перед переключением отсекает многие случаи отката npm, но не превращает наблюдение в транзакцию с npm.

**Пауза:** срок обнаружения, подготовка и ожидание текущей операции отделены от паузы между процессами. В тестах с локальными доступными зависимостями пауза должна укладываться в 15 секунд; это проверяемая цель, не обещание времени подключения реальных сервисов.

## 2. Почему требуется изменить запуск

Сегодня `bin/hse-harness.mjs run` импортирует `dist/main.js` из установленного npm-пакета, а `ServiceControl.start()` запускает тот же файл отдельным Node-процессом. Systemd также ссылается на файл внутри npm-prefix. Во время npm-обновления этот каталог заменяется поэтапно, включая зависимости. Даже работающий процесс может позднее импортировать модуль из уже изменённого дерева.

До изменения обработчики SIGINT/SIGTERM в `src/main.ts` сразу прерывали запрос Pi и закрывали Telegram. Это не обеспечивало протокол безопасного обновления. Состояние сохраняется в `data/operations.json`, Pi — в JSONL. Реализация 0.2.0 добавляет handshake готовности, протокол управления worker и проверку совместимости форматов.

Обновление не реализуется заменой `import`, очисткой кеша модулей, запуском второго обработчика Telegram или перезапуском сервиса из npm `postinstall`.

## 3. Выбранная архитектура

Постоянный управляющий процесс (**supervisor**) работает из личного каталога вне npm-prefix. Он запускает один рабочий процесс (**worker**) из завершённого каталога конкретного выпуска. Обновляемая глобальная установка служит сигналом нужной версии и содержит CLI.

```text
Глобальный npm-пакет: версия, установленная пользователем
                │ наблюдение, без исполнения из этого каталога
                ▼
Стабильный supervisor в HSE_HARNESS_HOME/runtime
                │ загрузка и проверка конкретного выпуска
                ▼
Неизменяемый каталог выпуска ──► единственный worker
                                      │
                                      ▼
                         существующие data/ и secrets/
```

«Неизменяемый» означает: приложение и его инструменты не пишут в каталог выпуска; npm устанавливает только в новый временный каталог. Это не защита от владельца ОС, который сам меняет файлы.

Две альтернативы отклоняются для первого режима:

| Вариант | Причина |
| --- | --- |
| Следить за `package.json` и перезапускать из глобального дерева | Manifest может появиться раньше зависимостей и окончания npm. Проверка стабильного размера/mtime не доказывает завершение установки. |
| Копировать глобальный `node_modules` после нескольких спокойных проверок | Копия может содержать части двух установок; npm может продолжить lifecycle или откат. Для достаточной проверки потребуется самостоятельная полная верификация дерева. |
| Выполнять `sudo systemctl restart` из npm lifecycle | Зависит от политики выполнения scripts, интерактивных прав и места установки; не позволяет сначала завершить учебную операцию. |

Выбранный способ требует отдельной подготовки выпуска и дискового места, зато сохраняет текущий код во время внешнего npm-обновления.

## 4. Каталоги и владельцы данных

```text
HSE_HARNESS_HOME/                 # по умолчанию ~/.hse-harness
  .env
  config.local.json
  data/                          # operations.json и JSONL, прежняя память
  secrets/
  runtime/
    launcher.mjs                 # стабильный supervisor, только Node built-ins
    settings.json                # включение режима, без секретов
    state.json                   # журнал и указатели выпусков
    supervisor.lock
    releases/
      <version>-<integrity-id>/
        installation/            # отдельная npm-установка и её зависимости
        release.json             # проверенная идентичность/совместимость
        COMPLETE                 # последняя запись после успешной подготовки
    staging/
      <attempt-id>/
```

Настраиваемые `STUDY_DATA_DIR`, `STUDY_SECRETS_DIR`, `STUDY_CONFIG`, `DOTENV_CONFIG_PATH` сохраняются как абсолютные пути. Они не выводятся из текущего выпуска и не перемещаются при каждом переключении. Нельзя включать данные пользователя в архив выпуска.

Supervisor и worker работают от прежнего непривилегированного пользователя. Каталоги runtime и состояния — `0700`, служебные JSON/locks — `0600`. Исполняемые файлы сохраняют нужный execute bit. Пути с пробелами поддерживаются; дочерние команды запускаются массивом аргументов без shell.

У выпусков разные каталоги, без hardlink к глобальной установке. Runtime registry URL для этого публичного пакета фиксирован: `https://registry.npmjs.org/`. Доступы Telegram, почты и модели не передаются npm-процессу подготовки. Нужное для npm окружение формируется отдельно, с явным npm binary и без включения пользовательских токенов в логи.

На первом этапе поддерживаются Linux VPS с systemd и локальный foreground-запуск на macOS/Linux. Windows остаётся обычным запуском до отдельной проверки процессов и файловых операций; CLI не должен заявлять там поддержку этого режима.

## 5. Обнаружение и подготовка выпуска

### Наблюдение

Supervisor получает абсолютный путь **именно той постоянной глобальной установки**, через которую режим был установлен. Не ищет произвольный `node_modules` в cwd. После смены npm-prefix, Node через nvm или места установки нужно повторить установку режима; старый supervisor не должен наблюдать случайный другой пакет.

Основной механизм — опрос раз в 10 секунд. `fs.watch` можно использовать лишь как ускоряющий сигнал. ENOENT, незавершённый JSON и отсутствующий bin во время reify означают «установка меняется»; работающий выпуск не останавливается. Три одинаковых наблюдения версии — debounce, не доказательство завершения npm.

Автоматически принимаются только стабильные semver-версии того же имени пакета, выше активной, с поддерживаемым протоколом и форматом состояния. `latest` со служебной версией `0.0.0-stage`, prerelease, локальный Git-пакет, другой scope, одинаковая версия с другой integrity и понижение версии не запускаются автоматически. Пользователь может явно установить любой пакет, но автоматически исполняемый кандидат проходит этот контракт.

Если установленные версии быстро меняются, держать только последний наблюдаемый подходящий кандидат. Подготовка отменяется между шагами без воздействия на worker. После начала переключения транзакция завершается или откатывается; следующая версия ставится в ожидание.

### Подготовка

1. Получить метаданные **точной версии**, не переопределять её через `latest`. Проверить имя, engines, SRI, доступность архива, runtime manifest и правила совместимости.
2. Создать приватный `staging/<attempt-id>` на том же filesystem, где будут releases.
3. Загрузить точный опубликованный архив, проверить SRI до исполнения его кода. Контрольная сумма подтверждает совпадение с реестром, а не отсутствие вредоносного кода.
4. Установить этот проверенный архив в staging отдельным npm-процессом. Успешное завершение **этого** процесса обязательно. Это не установка поверх текущего worker.
5. Проверить полный требуемый runtime, bundled-зависимости, совпадение версий с манифестом выпуска, platform dependencies и локальный запуск preflight. Не использовать TypeScript/dev dependencies пользователя.
6. Выполнить только явно проверенную платформенную подготовку, описанную ниже; итоговый runtime обязан успешно импортировать SDK и выполнить необходимые инструменты на текущей платформе.
7. Записать `release.json`, затем `COMPLETE`; завершить запись файлов и атомарно переименовать staging в конечный уникальный каталог. Только после этого выпуск допустим для запуска.
8. Непосредственно перед drain перечитать глобальную версию и настройки режима. Если источник вернулся к прежней версии, режим выключен или появился другой кандидат, старый worker продолжает работу.

**Выбранная политика npm 11/12:** установить проверенный локальный архив отдельным global prefix staging с отключёнными lifecycle:

```sh
npm install --global --prefix <staging-installation> <verified-local-tgz> \
  --omit=dev --ignore-scripts --no-audit --no-fund \
  --registry=https://registry.npmjs.org/
```

Реальный запуск использует argv, не shell-строку. Optional зависимости не отключать. npm `--allow-scripts=esbuild` не является решением для bundled esbuild в npm 12. После установки выполнить настоящее `esbuild.transform`, а не только import. Если platform binary требует подготовки, supervisor запускает только проверенный `node <release>/node_modules/esbuild/install.js`: версия и hash скрипта входят в audited bootstrap policy выпуска, manifest и ожидаемые binary hashes проверяются, overrides вроде `ESBUILD_BINARY_PATH` удалены. Дождаться завершения, повторить transform и SDK/tool smoke. Остальные lifecycle не исполняются. Неизвестный bootstrap/version либо отключение этой явной политики владельцем означает pending, без drain.

Это не произвольное разрешение npm scripts и не обход, скрытый от владельца: состав разрешённой платформенной подготовки документируется при выпуске. Никаких фоновых вопросов npm, `sudo` или `dangerously-allow-all-scripts`. Политика проверяется настоящей установкой Linux-архива на Linux и macOS с npm 11/12; текущее исследование исходников не считается такой проверкой. [npm 12 scripts policy](https://github.com/npm/cli/blob/v12.2.0/workspaces/arborist/lib/script-allowed.js).

Runtime manifest архива содержит inventory требуемых файлов/зависимостей и hash разрешённого bootstrap. После платформенной подготовки создать отдельный inventory **итогового** установленного дерева, учитывающий разрешённые изменения бинарников. Reuse/повторный запуск release проверяет этот inventory; не сравнивает платформенные изменения с исходным архивом как повреждение и не игнорирует повреждение прочих файлов.

Ошибки загрузки, отсутствие metadata/SRI, отсутствие npm, права каталога, несовместимый Node, нехватка места и отказ preflight не затрагивают worker. Повторы временных ошибок: через 1, 5 и 15 минут, далее раз в час. Изменение кандидата сбрасывает backoff. Постоянный отказ integrity/совместимости требует новой версии или явного повторения после устранения причины.

При отмене/timeout подготовки сначала остановить собственный npm/bootstrap child и дождаться `close` всех его управляемых descendants; лишь затем удалять staging. Installer использует отдельную process group, чтобы сигнал не затронул worker. После ограниченного ожидания допустим kill **только собственного staging installer**, не учебного worker. Если прекращение записи не доказано, staging не удаляется и не используется, причина сохраняется. Отмена обновления не оставляет фоновый npm, который дописывает следующий release.

## 6. Протокол процесса

IPC между supervisor и его worker не публикуется в сеть. В каждом сообщении есть `protocolVersion`, `attemptId`, уникальный `workerId` и тип. Supervisor принимает сообщения только от текущего ChildProcess и ожидаемого worker/attempt. Размер и форма сообщений проверяются; в IPC нет токенов и истории разговора.

| Сообщение | Смысл |
| --- | --- |
| `prepare` → `boot-ready` / `boot-failed` | Локальные проверки версии/конфигурации/формата состояния завершены; учебная работа ещё не разрешена. |
| `activate` → `active` | Worker может подключаться и выполнять учебную работу; подтверждает включение циклов. |
| `drain` → `draining` → `quiescent` | Новая работа не начинается; все начатые операции и записи завершены. |
| `resume` → `active` | Отменить ещё не завершённое переключение, продолжить старую версию. |
| `finish` → `exiting` + exit | Завершить уже drained процесс, закрыть подключения и освободить lock. |
| `health` | Heartbeat, режим, версия, in-flight и состояние интеграций; без учебного содержимого. |

IPC-команды идемпотентны по attemptId. Повторный `drain` не создаёт вторую транзакцию. `activate` не принимается в неподходящем состоянии. Heartbeat каждые 5 секунд; отсутствие heartbeat 30 секунд — диагностика зависания, **не разрешение** запускать второй worker.

Каждый управляющий запрос дополнительно имеет монотонный request sequence внутри attempt. `resume` аннулирует предыдущий drain и подтверждается `active` с его sequence. Поздний `quiescent` отменённого drain игнорируется и не разрешает `finish`. `finish` допустим только для текущего ещё не отменённого quiescent; после принятия finish возврат того же worker в active запрещён. Supervisor не начинает следующую попытку, пока исход отмены прежней не подтверждён.

Preflight отдельного кандидата не открывает Pi-сессию, не меняет state, не подключает пользовательский Telegram и не отправляет сообщения. Подготовка worker после ухода старого тоже не должна изменять учебное состояние до `activate`. Это позволяет безопасно отказаться от кандидата до начала работы.

`boot-ready` проверяет локальный код, зависимости, настройки и совместимость формата. Внешняя сеть, квота LLM и время ответа календаря не являются условием успешного обновления. Никаких платных пробных запросов модели. Недоступность интеграции отражается существующим degraded health и повторяется обычным приложением.

## 7. Завершение текущей работы: drain

В `src/main.ts` требуется явный lifecycle, общий для циклов, вместо одного `stopped` boolean. Все операции регистрируются до первого await; завершение и deregister — в finally. Контроль включает:

- Pi prompt, compaction, tool callbacks и запись JSONL;
- Bot API batch, обработку сообщений/подтверждений и сохранение offset;
- порции MTProto/IMAP, enqueue и сохранение курсоров;
- Scheduler transaction, send и запись delivered;
- approvals send/recover и изменения календаря;
- последовательную очередь Store.save и любые записи auth/session файлов.

После `drain`:

1. Не начинать следующий prompt, порцию источников, пакет уведомлений или callback с внешним эффектом. Уже начатую ограниченную операцию завершить.
2. Не закрывать MTProto и не вызывать `pi.abort()` посреди prompt, tool или одобренной отправки.
3. Long polling можно завершить/отменить отдельно от отправок. Уже полученные updates либо обработать с долговечным сохранением, либо оставить неподтверждёнными. Нельзя повысить offset выше не обработанного update.
4. Не требуется опустошать всю учебную очередь. Будущие элементы остаются на диске с теми же ID для новой версии.
5. Дождаться зарегистрированных операций, выполнить заключительное сохранение и `Store.flush()`. Ошибка любой незавершённой записи блокирует `quiescent`; её нельзя скрыть последующей удачной записью.
6. Дождаться завершения записи Pi и auth; после этого послать `quiescent`. В этом состоянии worker не пишет учебные данные до `resume` либо завершения.
7. Только по `finish` закрыть соединения, dispose Pi и освободить lock, затем завершить процесс. Новый writer запускается после наблюдаемого exit старого, а не после сообщения `exiting`.

Закрытие admission касается **новых корневых операций**. Уже принятый Pi turn получает scope и вправе последовательно вызвать оставшиеся tools, отправить финальный ответ и сохранить результат в этом scope. Так же принятый callback вправе завершить свою одобренную отправку. Каждая вложенная операция отслеживается, но не отклоняется только потому, что drain уже начался. Scope заканчивается после последнего внешнего результата и долговечной записи; без этого gate может незаметно превратить drain в abort.

Все retry sleeps должны реагировать на lifecycle. Граница long poll и batch обязана проверяться до следующего элемента. Обновление не должно ждать бесконечного retry на недоступную сеть.

Бюджет drain — 120 секунд. Если операция ещё идёт, supervisor отменяет попытку, возвращает старому worker разрешение выполнять работу и повторяет не раньше чем через 10 минут. По истечении бюджета автообновление **не** делает abort или SIGKILL. Одно уведомление объясняет отложенное обновление; не уведомлять при каждом poll.

После принятия `finish` ждать exit не более 30 секунд до регистрации blocked. Второй worker запрещён, пока прежний процесс существует; после принятого finish не посылать resume и не пытаться оживить disposed Pi/полузакрытый transport. Если старый процесс позднее завершится, supervisor может восстановить подтверждённый предыдущий выпуск отдельным worker. Не убивать активную учебную операцию ради установки версии. Аварийная ручная остановка остаётся отдельным действием пользователя.

Двухфазность обязательна: `drain/quiescent` ещё обратимы и не закрывают transport/Pi; принятие `finish` — точка необратимого закрытия. Внешний SIGINT/SIGTERM отменяет продвижение кандидата и останавливает собственных детей; после запроса пользователя stop supervisor не запускает replacement/rollback в фоне.

Если в ближайшие 60 секунд ожидается известное напоминание, переключение отложить, дать scheduler выполнить due работу и переоценить время. Это уменьшает риск задержки, но не заменяет восстановление overdue заданий после паузы.

## 8. Журнал переключения и recovery

Supervisor ведёт `runtime/state.json`, отдельно от `operations.json`. Только supervisor пишет этот журнал. Настройки режима пишутся CLI отдельно. Не хранить в журнале учебные тексты или секреты.

Минимальные поля:

```text
schemaVersion, supervisorVersion, protocolVersion
installation: { packageName, manifestPath, registry }
active: { version, integrity, releasePath }
previous: { version, integrity, releasePath } | null
attempt: { id, from, to, phase, requestSequence, startedAt, failure?,
           candidateStartCount, candidateFatalCount, rollbackStartCount,
           workerIncarnation, nextRetryAt, activationObserved? } | null
quarantine: [{ version, integrity, reason, createdAt }]
manualHold: { version, integrity, reason, createdAt } | null
lastObservedVersion, lastSuccessfulSwitch, deferredReason
```

Рабочий PID и nonce могут быть диагностическими полями, но не достаточным основанием считать другой процесс своим и посылать ему сигнал. Persistent timestamp не используется как доказательство, что worker жив.

Фазы: `preparing → prepared → draining → old-exiting → starting → probation → committed`; альтернативы `deferred`, `rolling-back`, `rolled-back`, `blocked`. Запись фазы и её from/to предшествует необратимому действию. Pointer active/previous/attempt меняется одной атомарной записью. Temp file, fsync файла, rename и синхронизация родительского каталога где поддерживается — единая операция хранения; неподдерживаемую платформенную гарантию нельзя выдавать за доказанную.

`active` остаётся предыдущим подтверждённым выпуском до commit, `attempt.to` определяет пробуемый. После local readiness и `activate` начинается probation: требуются **непрерывные 120 секунд одного worker**, живого и отвечающего по IPC без fatal runtime ошибок. Время внутри процесса измеряется monotonic clock; wall timestamps используются для журнала/retry, не для засчитывания downtime. После перезапуска worker или supervisor probation начинается заново, но сохранённый счётчик fatal/попыток не сбрасывается. Во время probation данные уже меняются и должны сохраняться; rollback не восстанавливает старые данные.

При старте supervisor:

- Удалить только собственные незавершённые staging, которые не принадлежат живой подготовке. Подготовленные COMPLETE releases не удалять по возрасту без проверки ссылок.
- Сначала получить supervisor lock и доказать отсутствие другого writer. Нельзя сбрасывать `service.lock` только из-за старой даты или неизвестного PID.
- Если кандидат ещё не был активирован, загрузить подтверждённый active. Если активация могла произойти, прочитать актуальный state, проверить совместимость и решить recovery по журналу; никогда не использовать ранний data snapshot.
- Если probation был прерван перезагрузкой машины без признаков ошибки кандидата, возобновить probation подготовленного совместимого кандидата. Если записан boot/fatal отказ, продолжить rollback.
- После commit стартовать active независимо от наличия глобального npm-каталога. Если глобальную установку удалили, наблюдение приостанавливается; работающий выпуск сохраняется.

Границы каждого файлового шага должны проверяться fault injection: падение до и после rename, отправки IPC, exit и commit.

## 9. Откат, зависания и несовместимость

### Критерии отказа

Синтаксическая ошибка, отсутствующий runtime import, несовместимый manifest, fatal ошибка локальной загрузки и преждевременный exit до активации — отказ кандидата. Startup timeout до local readiness — 30 секунд. До `activate` кандидат не имеет внешних эффектов: после штатной попытки остановки допустимо прекратить такой процесс, освободив только доказанно принадлежащий ему lock.

После активации: максимум три неожиданных fatal exit за probation либо однозначная внутренняя fatal ошибка запускают rollback. Worker с работающим IPC, но недоступной моделью/Telegram/почтой/календарём не считается плохим выпуском. Heartbeat timeout после активации не даёт права насильно откатиться поверх живого writer: требуется штатный drain, при невозможности — blocked и явная диагностика.

Для этого ошибки имеют типизированный источник: `release/protocol/state-invariant` против `provider/network/auth/quota`. Откат не определяется regex по тексту HTTP/LLM ошибки. Неожиданная ошибка внутреннего кода не должна бесконечно скрываться под `status('Модель', error)`; fatal сигнал/uncaught exit учитывается supervisor. При неизвестной причине — diagnosis/degraded без утверждения, что сеть доказывает плохой выпуск.

Уточнение бюджета: ошибка до первой активации сразу откатывает попытку. После активации первый и второй неожиданный exit допускают последовательный restart того же кандидата с backoff 10/30 секунд; третий — quarantine и rollback. Count сохраняется до запуска следующего child. Recovery подтверждённого предыдущего выпуска допускает максимум три запуска с задержками 10/30/60 секунд; исчерпание бюджета сохраняется как blocked и не сбрасывается systemd restart. Счётчики очищаются лишь после успешного commit здорового выпуска либо явного retry выбранного кандидата владельцем. Перезагрузка машины не сама по себе fatal кандидата, но также не считается успешной probation.

При отказе запуска сразу возвращается предыдущий подтверждённый выпуск. При отказе после начала работы сначала убедиться, что новый writer завершён; живой кандидат проходит тот же drain. Во время недоступности предыдущей версии не образуется бесконечный цикл переключений: не более трёх запусков с backoff, затем blocked, журнал и stderr сохраняются, systemd может восстановить supervisor.

Плохая пара version+integrity помещается в quarantine и не повторяется каждым poll. Новая версия проверяется независимо; ручная команда retry снимает только выбранный отказ и не отключает проверки.

### Совместимость данных

Выпуск содержит `runtime-manifest.json`: имя/версию пакета, protocol version, minimum supervisor version, supported Node/platform, версию формата operations, правила чтения/записи и идентичность Pi/runtime зависимостей.

Первый управляемый baseline получает protocol 1 и явный формат состояния. Читает существующий unversioned operations как legacy, сохраняет все прежние поля/ID. Миграция baseline проводится при первом штатном включении. После этого auto-update первого режима допускает только выпуски, совместимые в обе стороны с активной версией по operations, Pi JSONL, approvals, calendar metadata и auth format.

Поля формата должны означать реальную проверяемую совместимость, а не только равные числа. Добавление обязательного поля, изменение семантики ID, смена версии Pi с неизвестной совместимостью JSONL или невозвратимая auth migration блокируют автоматический переход. Такой выпуск требует отдельного обслуживаемого обновления; штатная память Pi не меняется ради этого режима.

Откатывается код, не `data/`, не JSONL и не удалённый календарь. Даже если новая версия уже добавила событие или отправила одобренный вопрос, старая продолжает с последними сохранёнными ID. Snapshot до обновления годится для ручного восстановления после анализа внешних последствий, не для автоматического rollback.

Автоматическое понижение по глобальному manifest запрещено. Ручной `hse-harness updates rollback` возможен только к проверенному сохранённому выпуску, с тем же drain и проверкой текущего state. Установка старой версии через npm сама по себе не должна тайно вернуть старый код.

Успешный ручной rollback сохраняет `manualHold` для версии/integrity, оставшейся установленной глобально: observer не применяет её снова через 10 секунд. Hold снимается при явном `updates retry` этой цели или обнаружении и подготовке **другой более новой** версии; обычный `enable` лишь включает наблюдение и не снимает hold/quarantine. Выбранный предыдущий выпуск проверяется против actual current state/JSONL, включая изменения всех промежуточных выпусков; совместимость A→B и B→C не доказывает возможность C→A.

## 10. Сообщения, память и внешние эффекты

Штатное переключение завершается после известных результатов уже начатых операций. Сохраняются botOffset, Telegram/IMAP cursors, seen, queue IDs, delivered, jobs, approvals/randomId, calendarTokens, bootstrapFinished, notices и sessionPath. Pi sessionPath остаётся в data/sessions, не внутри releases. Обновление не запускает заново историю с 1 сентября и не сбрасывает первоначальную сверку.

Получение Bot API update и повышение offset должны быть связаны с долговечной обработкой. Для текстового enqueue нужен устойчивый ключ по update_id: повтор после crash между enqueue и offset не создаёт второй owner turn. Для callback повтор должен попадать в сохранённый approval, а не создавать новую отправку. Минимальные receipt/operation записи относятся к надёжности существующей очереди, не к новой модели памяти.

После активации scheduler переоценивает текущий момент: прошедшие во время паузы интервалы объединяются по существующему правилу срочности, не отправляются как несколько своевременных напоминаний. Уже сохранённые перенос/отмена/«сдал» и актуальный доступный календарный snapshot учитываются прежде отправки; отметки delivered не сбрасываются. Новые сырые сообщения в очереди ещё могут требовать Pi для понимания: они приоритетны, но известные напоминания не ждут их бесконечно при исчерпанной квоте или недоступной модели. Не обещать учёт статуса из ещё не обработанного текста; health/status объясняют backlog.

Сводки перестают зависеть только от проверки `hour === 10/20`: устойчивый ID — дата Europe/Moscow + вид сводки. Если сегодняшняя сводка не доставлена/не стоит в очереди, догнать её в пределах двух часов после 10:00/20:00 с отметкой задержки. Уже сохранённую очередь проверить по тому же ID, не создавать второй элемент. За пределами окна не выдавать вчерашнюю/устаревшую сводку за текущую: сохранить отметку пропуска и показать её в status/следующем доступном уведомлении. Входившие в неё известные дедлайны продолжают обслуживаться scheduler независимо от сводки. Текст поздней сводки строится по актуальным данным, не копируется из старого черновика.

Одобренные вопросы используют прежний MTProto random_id и идентичный чат/текст. Изменения календаря сохраняют стабильный UID/ID, операции и условия конфликта; нельзя повторять неподтверждённое изменение расписания. Отказ обновления не предоставляет новых прав.

При аварийном kill/crash после принятой внешней отправки, но до её долговечной записи исход может быть неизвестен. Bot API `sendMessage` не предоставляет приложению универсальный idempotency key. Гарантия ровно одной отправки в этом окне не заявляется. Протокол штатного обновления обязан избегать такого kill; аварийное recovery сохраняет существующие безопасные ID и сообщает об неоднозначных исходах вместо заявления об успешной доставке. Уведомления могут повториться, но нельзя пропустить ещё не подтверждённую доставку только для красивой статистики.

Минимальный журнал внешних операций расширяет существующий operations.json: stable semantic ID, payload/target hash, `pending/sending/sent/unknown`, result/receipt и timestamp. Intent сохраняется до вызова, результат — после ответа. Для Bot API сохранять возвращённый message_id и отдельный receipt каждой части длинного ответа. Pi turn хранит фазу и подготовленный финальный ответ: если prompt завершён, но отправлены не все части, recovery продолжает доставку и не запускает модель заново без необходимости. `unknown` личного напоминания допускает повтор с пометкой возможного дубля; unknown календарной записи сначала проверяется чтением текущего ресурса и конфликтов. Одобренный вопрос восстанавливается через тот же approval/randomId. Это ограниченное усиление надёжности уже существующих операций, не общий workflow engine.

Во время короткой паузы новые личные сообщения остаются в Telegram до возобновления polling. Это не бессрочный архив: Bot API хранит updates не более 24 часов. При продолжительном отказе сообщить о риске и не обещать полное восстановление личного диалога. [Правила получения updates](https://core.telegram.org/bots/api#getupdates), [MTProto random_id](https://core.telegram.org/method/messages.sendMessage).

## 11. Supervisor, systemd и ручной запуск

Systemd ExecStart ссылается на стабильный `runtime/launcher.mjs`, с абсолютным Node binary, home и выбранными путями данных. Во время обновления worker systemd не перезапускается. Весь supervisor с worker остаётся в одном cgroup; `KillMode=control-group` задаётся явно. Runtime shutdown сообщает worker причину и ждёт его завершения; политика TimeoutStopSec для ручной остановки документируется отдельно от 120-секундного drain обновления.

При смерти supervisor worker реагирует на разрыв IPC и прекращает приобретать новую работу, сохраняет начатую работу и завершается. Systemd до повторного старта обязан убрать прежнюю группу. В foreground новый supervisor не стартует writer, пока прежний worker/lock ещё жив; автоматически не посылает сигнал неизвестному PID.

PID locks дополняются случайной идентичностью владельца и явным release ownership. Lock освобождается только владельцем. Linux start identity/IPC можно использовать для доказательства принадлежности; на платформе без доказательства занятое PID считается конфликтом, а не разрешением украсть lock. Locks supervisor и worker имеют разные назначения.

Стабильный supervisor первой реализации использует только Node built-ins, protocol 1 и не зависит от обновляемого node_modules. Кандидат, которому требуется другой supervisor, остаётся pending с инструкцией обновить управляющий процесс. Бесшовное самообновление supervisor и Node/npm, смена ОС/пользователя и npm-prefix не входят в первый режим. Это ограничение особенно важно не скрывать под обещанием любого будущего `npm update`.

## 12. CLI, первоначальное включение и отключение

Реализованные команды:

```sh
hse-harness start                  # foreground supervisor для постоянной npm-установки
hse-harness service install        # stable supervisor на Linux
hse-harness updates status
hse-harness updates disable        # оставить текущий выпуск, не удалять память
hse-harness updates enable
hse-harness updates retry          # повторить подготовку конкретного pending кандидата
hse-harness updates rollback       # штатный откат к проверенному previous
```

Для новых постоянных npm-установок автоматическое применение включено при managed start. `disable` блокирует новые попытки; во время подготовки отменяет staging. Если отключение получено после выхода старого worker, транзакция должна вернуть работающий выпуск и затем остановить наблюдение, а не оставить бота без процесса.

Временно запущенный `npx`, clone/dev и `npm run dev` не включают наблюдение глобальных обновлений. `hse-harness run` сохраняет явно документированный direct worker для совместимости и внутреннего запуска; без supervisor он не обещает подхват обновлений. Worker-код получает путь/идентичность выпуска от supervisor, но не берёт произвольный entrypoint из Telegram/учебного источника.

**Переход с уже работающей 0.1.0:** эта версия не содержит observer и не может самостоятельно превратиться в новый процесс. Первый выпуск режима требует один раз штатно остановить старого бота, установить новую версию, создать исходный проверенный baseline и переустановить service/start. Если прежний процесс ещё жив, установщик отказывает до его завершения. Нельзя обещать, что первое `npm update` у запущенной 0.1.0 само включит режим.

`status` и `/status` показывают `installedVersion`, `runningVersion`, `supervisorVersion`, `updatesEnabled`, `phase`, `pendingVersion`, последнее переключение, причину defer/quarantine и health интеграций. CLI читает runtime state без ожидания LLM. Управляющие CLI-команды изменяют только настройки режима/запросы; доступ к управлению локальный и от владельца. В первой версии не добавляются административные команды в учебные группы.

В личном Telegram — одно сообщение об успешной смене с from/to; об откате/blocked/deferred — одно сообщение с причиной и дальнейшей командой. Supervisor не становится вторым Bot API sender: уведомление передаётся единственному worker. Если worker не может запуститься или Telegram недоступен, статус и stderr доступны локально; отправка откладывается до восстановления, секреты не попадают в текст. Обычный polling не спамит.

## 13. Ресурсы и очистка

У опубликованного 0.1.0 архив около 33 МБ, установка около 142 МБ. Режим добавляет минимум active, previous и staging; npm cache учитывается отдельно. Не обещать, что одного размера архива достаточно.

Подготовка требует резерв 750 МБ, ограничивает архив 64 МБ, распаковку 500 МБ и время каждой сетевой операции. Нехватка диска не удаляет active/previous ради новой версии. Настоящий ENOSPC остаётся обрабатываемым даже после предварительной проверки.

После успешного commit хранить active и последний подтверждённый previous. Каталоги, на которые ссылаются attempt, живой worker или recovery, защищены от GC. Очистка выполняется отдельно после commit и не изменяет результат обновления; ошибка удаления лишь диагностируется. Частично подготовленный выпуск без COMPLETE никогда не запускается.

Хеш ID проверяется при обращении к releasePath; путь должен находиться внутри runtime/releases. Не следовать произвольным symlink из runtime journal наружу. npm binary и Node paths проверяются; shell interpolation, cwd из учебного сообщения, публикация токенов и скачивание release URL из сообщения исключены.

Архитектура памяти Pi и календарные провайдеры не переорганизуются ради этой функции.

## 15. План реализации

1. **Контракт и baseline:** manifest protocol/data compatibility, startup без побочных эффектов, идентичность locks, Store.flush и сохранение receipts. Проверить прежний direct/source запуск.
2. **Drain:** worker lifecycle и контроль всех in-flight, отмена drain без abort, gates каждого цикла, сохранение Pi/операций. Отдельно тестировать callback, source batch и send→save.
3. **Release store:** exact archive/SRI, staged install npm 11/12, platform binaries, atomic COMPLETE и журнал, cleanup и несовместимость.
4. **Supervisor:** только один writer, IPC, readiness, activation/probation, rollback/recovery и quarantine; heartbeat не равен разрешению убить worker.
5. **CLI/systemd:** стабильный launcher, foreground, enable/disable/status/retry/rollback, перенос 0.1.0 и текущих путей. Автообновление не разрешает migration несовместимых данных.
6. **Приёмка:** реальное обновление глобального пакета в изолированном prefix, SDK/Pi, npm 11/12, Linux/systemd и macOS; failure injection по каждой фазе. Затем обновить docs и выпустить новую версию.

Включение режима в опубликованный пакет допускается после полного интеграционного пути; промежуточные изменения не должны выдавать неподготовленные process switching за работающую функцию.

Быстрые проверки: state machine/journal/IPC и fake clock. Process integration: настоящие Node worker, локальный HTTP npm registry и реальные npm-команды в temporary prefix, delayed/failed lifecycle fixtures. Runtime E2E: существующий scripted Pi SDK/Telegram/CalDAV набор расширяется обновлением между версиями с настоящей записью JSONL. Systemd проверяется не только `systemd-analyze verify`, но и реальным stop/parent crash/restart в изолированной Linux VM/контейнере с systemd. Живые учебные аккаунты в автоматических тестах не используются.

Регрессии: прежние `npm run check`, `test:e2e`, `test:package`; source CLI, installed CLI, imports авторизации и памяти, foreground Ctrl+C, service stop, все календарные провайдеры. Тест одной версии без реальной смены пакета не считается доказательством этой функции.

## 17. Условия завершения

Режим готов, когда опубликованный тестируемый выпуск устанавливается обычным npm, включается один раз на baseline и последующее настоящее `npm update -g` автоматически переключает работающего бота; принятие/отложение/rollback видны в CLI и Telegram, полная тестматрица не выявляет потери сохранённого состояния или второго writer.

Документация содержит первоначальный переход с 0.1.0, пределы паузы и отката, несовместимые изменения supervisor/data, дополнительные расходы диска и ограничения внешних отправок. Публикация режима без этих условий не считается выполнением задачи.

## 18. Реализация и границы проверки

Код 0.2.0 выпущен: стабильный supervisor, immutable releases, IPC lifecycle, управление из CLI, systemd launcher, durable очередь и восстановление внешних операций. Operations получают формат 2 с чтением legacy 1/unversioned; штатные Pi JSONL и compaction остаются моделью памяти. Intent и receipts служат восстановлению операций, а не отдельной базе знаний.

Прошли typecheck, 118 тестов приложения, 41 runtime-тест release store/supervisor/installation, обычные и managed E2E и установка настоящего npm-архива с запуском CLI и daemon. Реальные global npm update и isolated install проверяются локальным HTTP registry с полными архивами проекта и тестовым worker; Pi SDK импортируется, esbuild выполняет настоящий transform. Этот тест измеряет переключение процесса, а не доступность живых учебных источников. Linux systemd и установка Linux-архива на macOS прошли в [CI выпуска](https://github.com/festy23/hse-harness/actions/runs/38423575081). Опубликован именно проверенный Linux-архив; SHA-512 архива из реестра совпадает с артефактом CI.

Таблица U01–U31 выше остаётся набором требований; число тестов не означает доказательство каждого возможного crash window. Внешние Telegram/CalDAV ответы и SDK модели в E2E задаются тестовыми источниками. Живые аккаунты, VPS пользователя и реальные лимиты подписки в этой реализации не подключаются. Если stale-lock recovery само прервано, оставшийся recovery guard требует локальной проверки владельцем: новый writer автоматически не запускается.

Bot outbox хранит pending/sending/sent и признак возможного повтора, calendar intents — pending/applied/notified/superseded/conflict. При потерянном ответе календаря worker читает текущую задачу до повторной записи; третье состояние вызывает конфликт. Одобренное изменение занятия сверяет актуальный preview и проверяет, не применено ли уже желаемое время. Устаревшее подтверждение не перезаписывает новые данные.
